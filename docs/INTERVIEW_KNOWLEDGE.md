# QualityPilot 面试知识沉淀

最后更新：2026-08-01

## 使用原则

- 本文档跟随开发过程持续更新，不是项目完成后临时整理的背诵稿。
- 只记录已经实现、实际测试或明确做过技术选型的内容。
- 每个重要功能应记录：业务问题、技术方案、选择原因、替代方案、风险、测试证据和后续优化。
- 性能、准确率、召回率和成功率等指标必须来自真实测试，不填写未经验证的数字。
- 面试表达重点是“为什么这样做、如何证明有效、出了问题如何定位”，而不只是罗列技术名词。

## 项目定位

QualityPilot 是面向 PCB 制造与 AOI 质量检测场景的质量异常分析和闭环处置智能体。目标流程是：

```text
异常输入
→ 意图识别与任务规划
→ 企业知识检索
→ 生产数据工具查询
→ 根因分析与证据汇总
→ 处置建议
→ 人工审批
→ 工单生成
→ 历史案例沉淀
```

项目重点不是普通聊天机器人，而是可追溯、可测试、可暂停恢复，并能安全调用业务工具的行业 Agent。

## 已沉淀的技术知识点

### 1. 健康检查与就绪检查的区别

当前实现分别提供：

- `/health`：只表示 FastAPI 进程能够响应。
- `/ready`：额外执行 `SELECT 1`，确认数据库连接可用。

面试表达：健康检查适合判断进程是否存活；就绪检查决定实例能否接收真实流量。数据库不可用时，进程可能仍然健康，但不应被认为已经就绪。

可能追问：

- 为什么不能只保留一个接口？
- 数据库查询超时时如何避免 readiness 长时间阻塞？
- Kubernetes 的 liveness、readiness 和 startup probe 应如何配置？

### 2. FastAPI lifespan 与资源管理

项目通过 lifespan 在启动时初始化数据库，在关闭时释放连接池。

设计价值：

- 把启动和关闭行为集中管理；
- 避免在模块导入阶段执行不可控的异步操作；
- 为后续模型客户端、任务队列和可观测性组件提供统一生命周期入口。

当前不足：启动阶段仍使用 `create_all()`，适合早期本地开发，但不能替代生产数据库迁移。

### 3. 异步 SQLAlchemy 会话

当前后端使用 `create_async_engine`、`async_sessionmaker` 和 FastAPI 依赖注入，为每个请求提供独立的 `AsyncSession`。

面试重点：

- 异步数据库访问避免请求线程在网络 I/O 时被阻塞；
- 每个请求拥有独立会话，路由层显式提交事务；
- `expire_on_commit=False` 便于提交后直接序列化 ORM 对象；
- `pool_pre_ping=True` 可以在取出连接时检查失效连接。

需要继续研究：事务边界、连接池大小、超时设置、并发写入冲突和异常后的 rollback。

### 4. PostgreSQL、pgvector 与数据建模

当前模型采用“文档主表 + 文档分块表”：

- 一个文档对应多个有序分块；
- `(document_id, chunk_index)` 保证同一文档内分块顺序不重复；
- 外键使用 `ON DELETE CASCADE`；
- `embedding` 当前允许为空。

为什么 Embedding 暂时为空：尚未固定嵌入模型。不同模型的向量维度可能不同，在模型选型前生成向量或固化索引会增加迁移成本。

当前实际环境已验证：PostgreSQL 17.10、pgvector 0.8.6，两张知识库表存在。

### 5. 为什么需要 Alembic

`Base.metadata.create_all()` 只适合创建缺失表，不能可靠表达字段修改、约束变化、数据迁移和版本回退。

本阶段已经核对实际数据库结构，为现有两张表建立 `0001_existing_schema` 基线，并通过 `0002_file_ingestion` 只增加文件元数据和分块偏移字段。迁移前后原有记录保持一致，整个过程没有删除表、数据库或数据卷。

可能追问：

- 已经存在的数据库如何安全接入 Alembic？
- baseline、stamp 和 upgrade 分别是什么？
- 如何审查自动生成的 migration？
- 数据量很大时如何增加非空字段或索引？

### 6. Docker 数据持久化

PostgreSQL 使用命名卷 `qualitypilot_pgdata` 保存数据。容器本身可以重新创建，但数据库数据不应依赖容器可写层。

安全规则：不得执行 `docker compose down -v`，因为 `-v` 会删除 Compose 管理的数据卷。

可能追问：

- bind mount 和 named volume 的区别是什么？
- 如何备份和恢复 PostgreSQL？
- 开发、测试和生产数据库如何隔离？

### 7. Git 与单仓库管理

Git 仓库建立在 QualityPilot 项目根目录，因此后端、前端、MCP 服务、测试、文档、脚本和脱敏数据集都可以在同一个仓库中演进。

当前安全措施：

- 忽略 `backend/.env`；
- 忽略 `backend/.venv`；
- 忽略运行时上传目录；
- 提交前检查敏感路径；
- `main` 跟踪 GitHub 私有仓库的 `origin/main`。

- Docker 容器健康状态；
- PostgreSQL 和 pgvector 版本；
- API 成功响应与状态码；
- Pydantic 参数校验；

测试时创建的记录使用独立 UUID 和 `source_type=test` 标记，验证后精确删除，最终确认没有测试数据残留。

当前已经使用 pytest、pytest-asyncio 和 httpx 建立 21 项自动化测试，覆盖解析、切分、大小限制、现有接口回归、真实 PostgreSQL 上传查询和事务回滚。集成测试仍使用开发数据库并精确清理，下一步需要独立测试数据库和 CI。测试过程中还定位了异步连接池跨事件循环复用问题，最终通过会话级 pytest 事件循环统一管理全局异步资源。

### 9. 文件上传、解析、切分与事务一致性

本阶段采用分层实现：路由负责 HTTP 协议，导入服务负责大小限制和流程编排，解析器负责格式适配，切分器负责文本边界，文件存储服务负责生成安全名称和原子落盘。

关键设计与面试知识：

- 上传内容按块读取，累计超过 20 MB 立即返回 413，不能只信任请求头中的文件大小。
- 文件名会移除路径部分，存储时使用 UUID 名称，避免路径穿越、同名覆盖和用户文件名直接落盘。
- PDF 检查 `%PDF-` 签名，DOCX 检查 ZIP 签名，TXT/Markdown 拒绝 NUL 二进制内容。
- TXT/Markdown 支持 UTF-8 与 GB18030；PDF 和 DOCX 最终都转换成统一纯文本。
- PDF/DOCX 解析放入工作线程，避免 CPU/同步库阻塞 FastAPI 事件循环。
- 切分目标约 800 字符、重叠 100 字符，优先在中文句号、问号、分号和换行处结束。
- 每个分块记录 `chunk_index`、`char_start` 和 `char_end`，为引用溯源和后续评测保留依据。
- 文档元数据与全部分块放在一个数据库事务中；唯一约束故障测试证明分块失败时文档也会回滚。
- 原文件落盘不是数据库事务的一部分，因此数据库写入失败时必须执行补偿删除。
- SHA-256 用于内容追溯和后续重复检测，但当前没有直接把相同哈希设为唯一约束，因为同一文件可能需要以不同业务上下文重复导入。

真实验证：现有数据库完成纯增量迁移；21 项自动化测试全部通过；真实 HTTP 上传 10,930 字节 TXT 后生成 9 个有序分块，测试数据和文件均已清理。

可能追问：

- 为什么文件系统与数据库无法天然组成一个 ACID 事务？
- 同步导入何时需要升级为任务队列？
- 如何防止 ZIP bomb、扫描 PDF 无文本和恶意超大页面？
- 字符切分与 tokenizer 切分各有什么优缺点？
- 如何保证重试不会生成重复文档？
- 大批量分块写入为什么要使用批量 INSERT？
