## 使用原则

- 本文档跟随开发过程持续更新，不是项目完成后临时整理的背诵稿。

## 项目定位

QualityPilot 是面向 PCB 制造与 AOI 质量检测场景的质量异常分析和闭环处置智能体。目标流程是：

```text
异常输入
→ 意图识别与任务规划
→ 企业知识检索
→ 生产数据工具查询
→ 根因分析与证据汇总
→ 处置建议
→ 人工审批
→ 工单生成
→ 历史案例沉淀
```

项目重点不是普通聊天机器人，而是可追溯、可测试、可暂停恢复，并能安全调用业务工具的行业 Agent。

## 已沉淀的技术知识点

### 1. 健康检查与就绪检查的区别

当前实现分别提供：

- `/health`：只表示 FastAPI 进程能够响应。
- `/ready`：额外执行 `SELECT 1`，确认数据库连接可用。

面试表达：健康检查适合判断进程是否存活；就绪检查决定实例能否接收真实流量。数据库不可用时，进程可能仍然健康，但不应被认为已经就绪。

可能追问：

- 为什么不能只保留一个接口？
- 数据库查询超时时如何避免 readiness 长时间阻塞？
- Kubernetes 的 liveness、readiness 和 startup probe 应如何配置？

### 2. FastAPI lifespan 与资源管理

项目通过 lifespan 在启动时初始化数据库，在关闭时释放连接池。

设计价值：

- 把启动和关闭行为集中管理；
- 避免在模块导入阶段执行不可控的异步操作；
- 为后续模型客户端、任务队列和可观测性组件提供统一生命周期入口。

当前实现：应用启动时只执行数据库连接检查，表结构变更已交由 Alembic 管理，不再依赖 `create_all()` 修改现有数据库。

### 3. 异步 SQLAlchemy 会话

当前后端使用 `create_async_engine`、`async_sessionmaker` 和 FastAPI 依赖注入，为每个请求提供独立的 `AsyncSession`。

面试重点：

- 异步数据库访问避免请求线程在网络 I/O 时被阻塞；
- 每个请求拥有独立会话，路由层显式提交事务；
- `expire_on_commit=False` 便于提交后直接序列化 ORM 对象；
- `pool_pre_ping=True` 可以在取出连接时检查失效连接。

需要继续研究：事务边界、连接池大小、超时设置、并发写入冲突和异常后的 rollback。

### 4. PostgreSQL、pgvector 与数据建模

当前模型采用“文档主表 + 文档分块表”：

- 一个文档对应多个有序分块；
- `(document_id, chunk_index)` 保证同一文档内分块顺序不重复；
- 外键使用 `ON DELETE CASCADE`；
- `embedding` 当前允许为空。

为什么 Embedding 允许为空：新上传文档已经自动生成向量，但旧数据、人工创建的空文档以及失败后待重试的分块仍需要可空字段。单文档回填接口只处理空向量，允许分阶段完成历史数据向量化。

当前实际环境已验证：PostgreSQL 17.10、pgvector 0.8.6，两张知识库表存在，`embedding` 字段为可空的 `vector(1024)`。

### 5. 为什么需要 Alembic

`Base.metadata.create_all()` 只适合创建缺失表，不能可靠表达字段修改、约束变化、数据迁移和版本回退。

本阶段已经核对实际数据库结构，为现有两张表建立 `0001_existing_schema` 基线，并通过 `0002_file_ingestion` 只增加文件元数据和分块偏移字段。迁移前后原有记录保持一致，整个过程没有删除表、数据库或数据卷。

安全规则：不得执行 `docker compose down -v`，因为 `-v` 会删除 Compose 管理的数据卷。

### 9. 文件上传、解析、切分与事务一致性

本阶段采用分层实现：路由负责 HTTP 协议，导入服务负责大小限制和流程编排，解析器负责格式适配，切分器负责文本边界，文件存储服务负责生成安全名称和原子落盘。

关键设计与面试知识：

- 上传内容按块读取，累计超过 20 MB 立即返回 413，不能只信任请求头中的文件大小。
- 文件名会移除路径部分，存储时使用 UUID 名称，避免路径穿越、同名覆盖和用户文件名直接落盘。
- PDF 检查 `%PDF-` 签名，DOCX 检查 ZIP 签名，TXT/Markdown 拒绝 NUL 二进制内容。
- TXT/Markdown 支持 UTF-8 与 GB18030；PDF 和 DOCX 最终都转换成统一纯文本。
- PDF/DOCX 解析放入工作线程，避免 CPU/同步库阻塞 FastAPI 事件循环。
- 切分目标约 800 字符、重叠 100 字符，优先在中文句号、问号、分号和换行处结束。
- 每个分块记录 `chunk_index`、`char_start` 和 `char_end`，为引用溯源和后续评测保留依据。
- 文档元数据与全部分块放在一个数据库事务中；唯一约束故障测试证明分块失败时文档也会回滚。
- 原文件落盘不是数据库事务的一部分，因此数据库写入失败时必须执行补偿删除。
- SHA-256 用于内容追溯和后续重复检测，但当前没有直接把相同哈希设为唯一约束，因为同一文件可能需要以不同业务上下文重复导入。

真实验证：现有数据库完成纯增量迁移；当前 52 项自动化测试全部通过；真实 HTTP 上传 10,930 字节 TXT 后生成 9 个有序分块，测试数据和文件均已清理。

### 10. 云端 Embedding 选型、配置安全与真实 API 排障

业务问题：文本分块需要转换成固定维度向量，才能进行语义相似检索。

技术方案：选择阿里云百炼 `qwen3.7-text-embedding`，显式指定 1024 维，后续使用 pgvector 余弦距离检索。云端 API 避免了在开发机安装 Ollama 和维护本地模型，但引入网络依赖、调用成本和数据合规风险。

配置安全：

- API Key 仅保存在被 Git 忽略的 `backend/.env`，`.env.example` 只保留空占位符和公共默认值。
- Pydantic Settings 使用 `SecretStr | None`；普通打印只显示星号，同时允许健康检查和不调用模型的测试在无真实密钥环境运行。
- 维度、批量大小和超时时间使用有类型的配置字段与范围校验。

关键实现：

- 业务层依赖 `EmbeddingProvider` 协议，不直接依赖百炼客户端；工厂负责从 Settings 创建具体 Provider。
- 文档列表按配置的批量大小拆分请求，并根据响应 `index` 恢复输入顺序。
- 超时、网络异常和远端非成功状态分别映射为领域异常；网络异常、超时、429 与 5xx 使用可配置次数的指数退避重试，配置错误、4xx 参数错误和响应契约错误不重试。
- 响应在入库前校验数量、索引唯一性、1024 维约束以及 NaN/Infinity 等非法数值。
- 单元测试使用 `httpx.MockTransport`，验证 Provider 协议而不访问真实 API。

真实验证：专属 OpenAI 兼容端点返回 HTTP 200、1 条 1024 维向量和 38 Token 统计；`SecretStr` 打印为 `**********`。FastAPI 上传与回填通过假 Provider 验证实际 1024 维 PostgreSQL 写入，全量 52 项测试通过，`alembic check` 无结构差异。

排障过程：

1. Shell 未加载 `.env` 时，URL 展开后只剩 `/embeddings`，`curl` 返回 `No host part in the URL`；通过 `%q` 检查非敏感变量并重新加载绝对路径解决。
2. 环境变量正确后，WSL 默认 TLS 握手返回 `SSL_ERROR_SYSCALL`，说明请求尚未到达 HTTP 业务层。
3. 强制 IPv4 和 HTTP/1.1 后，专属 Host、公共 Host 和阿里云官网均完成 TLS，真实 Embedding 调用返回 200。因为两个参数同时引入，只能把原因收窄到 IPv6 网络路径或协议协商兼容性，不能无证据地宣称已精确定位。

测试取舍：普通单元测试不直接调用真实云 API，以避免网络不稳定、密钥泄露、费用和限流；后续应注入假 Provider，真实 API 仅用于显式启用的集成或冒烟测试。

当前风险：

- 当前自动重试发生在同步 HTTP 请求内，可能增加响应时间；大规模回填仍需要持久化任务队列、任务状态、限流和可观测性。
- 云端调用需要考虑网络、限流、配额、脱敏、可观测性和降级策略。

### 11. 向量维度增量迁移与数据保护

业务问题：模型输出固定为 1024 维，但早期数据库字段定义为 `vector(1536)`。ORM 类型与实际数据库类型不一致会阻止正确入库，也会让后续索引和距离计算建立在错误结构上。

实施过程：

- 迁移前先只读检查实际数据库，确认 Alembic 位于 `0002_file_ingestion`，数据库有 1 条原有文档、0 条分块、0 条非空向量。
- ORM 的字段类型由 `Vector(1536)` 调整为 `Vector(1024)`，新增 `0003_embedding_1024` 增量迁移，没有删除或重建数据库、表和数据卷。
- 迁移脚本在修改类型前显式检查是否存在非空向量；如果存在则抛出异常，要求先设计重新嵌入或数据搬迁方案，避免数据库隐式转换造成不可逆的数据问题。
- downgrade 同样只允许在向量全部为空时执行，因为 1024 维向量不能直接变回有业务意义的 1536 维向量。
- 应用前检查了离线 SQL，确认只包含前置条件、字段类型变更和 Alembic 版本更新。

真实验证：迁移已在现有数据库升级到 `0003_embedding_1024`，字段类型为可空的 `vector(1024)`，原有 1 条文档记录保持不变。随后在显式事务中写入一条 1024 维临时向量，通过 `vector_dims` 验证维度后回滚，确认没有测试分块残留。`alembic check` 无待生成操作，当前全量 52 项自动化测试全部通过。

面试表达：数据库迁移不是简单修改 Python 类。应先调查真实数据，再通过版本化迁移表达结构变化；对可能损坏数据的类型变更增加可执行的前置条件，并分别验证迁移 SQL、真实升级、数据保留、目标类型写入和应用回归。

### 12. 上传自动向量化、重试与幂等回填

业务问题：仅有 Provider 和向量字段还不能形成可检索知识库。新上传分块需要自动写入向量，历史空向量需要可重复执行的回填入口，同时外部模型故障不能造成文件、文档或部分分块残留。

关键设计：

- 上传流程按“读取与解析 → 切分 → 云端向量化 → 原文件落盘 → 文档、分块和向量单事务写入”执行。云端调用位于数据库事务之前，避免在网络等待期间占用长事务。
- Provider 通过 FastAPI 依赖注入的是惰性工厂；格式或大小校验失败时不会创建客户端，测试可以替换为假 Provider。
- 网络错误、超时、429 和 5xx 按配置进行指数退避重试；不可重试错误立即失败。Provider 无论成功失败都会关闭自有 HTTP 客户端。
- 回填接口先查询目标并结束只读事务，只对 `embedding IS NULL` 的分块调用模型。写回再次附加 `embedding IS NULL` 条件，重复调用直接跳过已完成分块，并避免并发请求覆盖已有结果。
- 分块查询只返回 `has_embedding` 和 `embedding_dimension`，不把 1024 个浮点数直接暴露给前端。
- 上传向量失败返回 502 或 503；由于向量化发生在文件保存和数据库事务之前，不会留下文件、文档或部分分块。

事务边界取舍：外部 API 无法加入 PostgreSQL 的 ACID 事务。本阶段选择先完成外部计算、再进行本地原子写入，获得简单明确的失败语义；代价是数据库最终写入失败时已经消耗了模型额度。生产级异步方案应使用任务表、幂等键、状态机和持久化重试队列。

真实验证：假 Provider 生成 1024 维向量后，上传接口把全部向量写入实际 PostgreSQL；分块查询返回维度 1024。历史回填首次写入 2 个分块，第二次返回写入 0、跳过 2，Provider 总共只调用一次。模拟网络故障连续失败时按配置调用 3 次，接口返回 503，数据库没有生成失败文档。全量 52 项测试通过，测试未访问真实百炼 API、未消耗 Token。

### 13. 余弦检索、HNSW 索引与引用结果

业务问题：向量写入数据库后，还需要把用户问题转换为同模型向量，按照语义接近程度检索分块，并返回足够的来源信息供后续 Agent 引用和人工核查。

关键实现：

- 新增 `POST /api/v1/knowledge/search`，请求包含去除首尾空白后的查询文本和 1—50 范围内的 `top_k`。
- 空知识库先执行非空向量存在性检查并直接返回空列表，不创建 Provider、不访问云端，也不消耗 Token。
- 非空知识库调用与文档相同的 Provider 生成查询向量，并复用超时、网络、429 和 5xx 重试策略。
- SQLAlchemy 使用 pgvector 的 `cosine_distance`，实际 SQL 运算符为 `<=>`；按距离升序取 Top-K，并用 `1 - cosine_distance` 返回余弦相似度。
- 结果不只返回正文，还包含 `chunk_id`、`document_id`、标题、来源类型、来源 URI、原文件名、分块序号和字符起止位置，为后续引用溯源保留证据。
- `0004_embedding_hnsw` 迁移创建只覆盖非空向量的 HNSW 索引，操作符类使用与余弦查询一致的 `vector_cosine_ops`。

索引取舍：HNSW 查询性能和召回表现通常优于精确全表扫描，但索引会增加内存、磁盘和写入成本，并且属于近似检索。当前先使用 pgvector 默认 HNSW 参数，不能在没有真实规模数据和评测集时编造性能提升或召回率。

真实验证：在实际 PostgreSQL 中插入三条 1024 维测试向量，查询向量与它们的余弦相似度分别为 1、0.8 和 0，接口按预期返回前两条，并正确携带文档来源与字符偏移。另在显式事务中插入 200 条临时非零向量，关闭顺序扫描后执行 `EXPLAIN`，查询计划显示 `Index Scan using ix_knowledge_document_chunks_embedding_hnsw_cosine`，随后事务整体回滚。当前全量 52 项测试通过，没有调用真实百炼 API。

重要边界：本次 `EXPLAIN` 只证明 SQL 形态能够使用索引，不等于生产数据规模下必然更快。后续必须用真实数据量执行 `EXPLAIN ANALYZE`，比较延迟、索引体积、构建时间和 Recall@K。

### 14. 检索评测集与质量指标

业务问题：只实现向量检索无法证明搜索质量。没有固定查询和相关性标注时，修改模型、切分、索引或排序策略后只能依赖主观感受，无法判断是否回退。

关键实现：

- 建立第一版合成脱敏 PCB/SOP 数据集，包含 5 份 Markdown 文档、8 条查询、稳定文档编号、相关文档标注和证据短语。
- Pydantic 在运行前校验文档编号、标题和查询编号唯一，并拒绝引用未知文档或空证据。
- 评测运行器逐条调用现有搜索 API，根据唯一标题映射稳定文档编号，不自动上传或删除数据。
- 指标模块与真实 HTTP 调用解耦，可以用固定命中结果做确定性单元测试。
- JSON 报告保留总体指标和逐查询结果，便于后续向量检索、全文检索、融合排序和 Rerank 使用同一基准比较。

指标定义：

- 文档级 Recall@K：Top-K 分块覆盖的相关文档去重数量除以标注相关文档总数。
- MRR：每条查询第一个相关分块排名的倒数，再对全部查询取宏平均。
- 引用正确率@K：命中分块必须来自相关文档，并包含该文档至少一个标注证据短语；先按查询计算正确分块占返回分块比例，再取宏平均。这是本项目的证据约束指标，不应冒充通用行业标准。

为什么先评测再做 BM25：固定基线可以证明后续改动带来的真实增益，也能暴露语义召回、精确术语匹配和引用证据之间的不同问题。

真实验证：经用户明确授权，通过真实 Uvicorn 上传接口导入 5 份合成文档，生成 5 个分块，并由 `vector_dims` 确认每个向量均为 1024 维。

真实百炼基线结果：Top-1 的 Recall、MRR、引用正确率均为 0.8750；Top-3 的 Recall 为 0.9375、MRR 为 0.9167、引用正确率为 0.3333。Q001—Q007 的正确文档均排第 1；Q008 要求两个相关文档，Top-3 只召回其中一个且排第 3。Top-3 引用正确率较低也受指标分母影响：多数查询只有一个相关分块，但固定返回三条，因此即使第一条正确也只有 1/3。

故障排查：首次运行 Top-1 时，前两条查询成功，第三条在后端 Provider 重试耗尽后返回 503，原评测运行器直接终止且不生成报告。随后为评测 HTTP 客户端增加有限指数退避，只重试网络错误、429 和 5xx，普通 4xx 不重试，并增加模拟 503 后成功的测试；重新运行后报告完整生成。

当前全量 52 项测试通过，`alembic check` 无结构差异。向量、关键词和混合检索逐查询报告均已保存；真实向量调用没有汇总 Token 用量，因此不编造成本数字。

风险和不足：

- 当前样例规模小且为合成数据，只适合开发回归，不能代表生产效果。
- 运行器按唯一标题把 API 结果映射到稳定编号；后续应在文档元数据中增加专门的数据集标识，避免同名文档干扰。
- 证据短语匹配是可解释的确定性检查，但无法识别同义改写，后续可以增加人工复核或独立评判模型。

- Recall@K、Precision@K 和 MRR 分别回答什么问题？
- 为什么评测相关性使用文档级标注，而检索返回的是分块？
- 为什么合成数据不能当成简历中的生产指标？
- 如何保证引入 BM25 或 Rerank 后的对比公平？

### 16. 中文关键词检索与 RRF 混合排序

业务问题：纯向量检索擅长语义相似，但对设备代码、缺陷名称、工艺参数等精确术语可能不稳定；只做关键词检索又难以覆盖同义表达。两种信号需要在保持来源可追踪的前提下组合。

技术方案：

- 第一版中文关键词检索选择 PostgreSQL 官方 `pg_trgm` 扩展，而不是直接使用内置英文导向的 `to_tsvector`。trigram 按字符片段计算相似性，无需额外中文分词服务，能覆盖中文短语、英文缩写和设备代码。
- `0005_trigram_search` 安装扩展并在分块正文创建 `gist_trgm_ops` 索引；查询使用 `<->>` word-similarity 距离进行 KNN 排序，并过滤完全没有字符片段重叠的结果。
- 搜索请求新增 `vector`、`keyword`、`hybrid` 三种模式，默认仍为 `vector`，保持旧客户端和已保存向量基线可复现。
- 返回值保留 `match_type`、`vector_score` 和 `keyword_score`，避免只有一个无法解释的综合分数。

为什么使用 RRF：余弦相似度与 trigram word similarity 的分布和量纲不同，直接相加需要脆弱的归一化与权重。Reciprocal Rank Fusion 只依赖各通道排名：每个候选累加 `1 / (rrf_k + rank)`，再按融合分数排序。本项目默认各通道等权、候选倍率 5、`rrf_k=60`，参数由 Pydantic Settings 校验。

索引排障：首次 EXPLAIN 仍然是顺序扫描。原因是 SQLAlchemy `CAST(distance AS FLOAT)` 改变了 ORDER BY 表达式，加上 UUID 次级排序后不再满足 GiST KNN 排序形式。改用只影响 Python 类型、不生成 SQL CAST 的 `type_coerce`，并移除次级排序后，计划变为 `Index Scan using ix_knowledge_document_chunks_content_gist_trgm`。事务内 200 条临时数据随后全部回滚。

真实同集评测：

- 向量 Top-1：Recall 0.8750、MRR 0.8750、引用正确率 0.8750。
- 关键词 Top-1：Recall 0.6875、MRR 0.7500、引用正确率 0.7500。
- 混合 Top-1：Recall 0.9375、MRR 1.0000、引用正确率 1.0000。
- 向量 Top-3：Recall 0.9375、MRR 0.9167、引用正确率 0.3333。
- 关键词 Top-3：Recall 1.0000、MRR 0.8750、引用正确率 0.5625。
- 混合 Top-3：Recall 1.0000、MRR 1.0000、引用正确率 0.3750。

结果解释：关键词 Top-1 弱于向量，但扩大候选后能补齐向量漏掉的相关文档；RRF 把互补候选提前，使混合 Top-1 三项指标均提升。Top-3 引用正确率仍受固定返回三条、每个查询通常只有一条证据分块的指标定义影响。

风险和不足：

- 评测只有 5 份合成文档和 8 条查询，提升只能作为开发基线，不能写成生产准确率。
- `pg_trgm` 是字符相似性，不理解词义，也不是 BM25；长文本、同义词和完全不同字面的表达仍依赖向量通道。
- 当前融合是固定等权 RRF；是否增加加权、Rerank 或中文分词必须由更大真实评测集决定。
- 混合模式需要调用云端查询 Embedding，网络失败语义与向量模式一致；关键词模式可作为不依赖云端的显式调用方式。

- 为什么不能直接把余弦相似度和关键词分数相加？

- `type_coerce` 与 SQL `CAST` 为什么会产生不同查询计划？

### 17. LangGraph 状态机、人工审批与运行时依赖

业务问题：质量处置 Agent 不能把“检索到证据”和“已经批准执行”混为一谈。流程必须保留证据、草稿和审批结果，并能在等待工程师判断时暂停。

关键实现：

- `POST /api/v1/agent/runs` 创建 UUID `run_id`，执行知识检索和证据草稿节点，然后在审批节点暂停并返回 202。
- `GET /api/v1/agent/runs/{run_id}` 查询证据、草稿、状态和审批结果。
- `POST /api/v1/agent/runs/{run_id}/approval` 恢复同一工作流；批准后才产生最终响应，拒绝后最终响应为空，重复审批返回 409。
- Agent 默认使用 hybrid 检索，也允许 vector 或 keyword，并保留文档、分块、来源和通道分数。
- 第一版生成器不调用大模型，只按确定性规则整理证据并附加风险提示。

状态设计：

- LangGraph 状态只包含 `run_id`、问题、检索模式、证据、草稿、状态和审批结果等可序列化数据。
- `AsyncSession`、Provider 工厂、检索器和生成器通过 `Runtime Context` 注入节点，不写入检查点。
- 审批节点使用 `interrupt` 暂停；恢复时以 `run_id` 作为 `thread_id`，通过 `Command(resume=...)` 注入审批结果。
- interrupt 所在节点恢复时会从节点开头重新执行，因此中断前不能放置发送工单、扣费等非幂等副作用。

边界与取舍：

- 第一版曾使用 `InMemorySaver` 验证流程语义；现已换成 PostgreSQL 检查点，内存实现只保留为工作流单元测试默认值。
- 检查点解决工作流恢复，不等于完整业务审计；当前还没有审批人身份、独立审批事件和保留期限。
- 批准当前只发布最终响应，不调用 MES/QMS、不生成真实工单。
- 外部检索或 Embedding 异常沿用现有 HTTP 错误映射；持久失败状态、重试历史和审计日志仍待实现。

真实验证：Agent 流程测试覆盖暂停恢复、批准拒绝、重复审批冲突、缺失运行记录、请求校验、关键词模式不调用 Embedding 和混合检索路径。运行中的 Uvicorn 完成关键词模式启动、状态查询和批准恢复，依次返回 202、200、200，检索 3 条证据并进入 completed；该冒烟未调用云端。

### 18. PostgreSQL 持久化检查点与进程恢复

业务问题：人工审批可能等待数小时。检查点若只在内存中，服务重启、热重载或多 Worker 切换都会使待审批任务消失，因此 API 不能可靠地按 `run_id` 恢复。

关键实现：

- 使用 `AsyncPostgresSaver` 保存 LangGraph 状态，FastAPI lifespan 在启动时打开 psycopg 异步连接池，在关闭时释放连接。
- SQLAlchemy 继续通过 asyncpg 处理业务 ORM；checkpointer 使用 psycopg，因为官方实现依赖 psycopg 的连接、行工厂和 pipeline 能力。两个连接池访问同一个 PostgreSQL，但生命周期和职责分离。
- 状态序列化显式使用 `JsonPlusSerializer(allowed_msgpack_modules=None)`，不允许环境变量扩大可反序列化模块范围。
- 连接池启用 `autocommit=True`、`dict_row` 和 `prepare_threshold=0`；最小、最大连接数由 Pydantic Settings 校验。

迁移所有权：

- 没有在应用启动时调用 checkpointer 的 `setup()`，因为项目约定所有数据库结构变更都必须经过 Alembic 审查。
- `0006_agent_checkpoints` 按当前固定版本 `langgraph-checkpoint-postgres==3.1.1` 建立官方检查点结构和迁移版本记录。
- Alembic 元数据登记同一结构，使 `alembic check` 能识别真实漂移；未来升级包版本时必须先比较其迁移定义，再新增项目迁移。
- downgrade 会先统计检查点、二进制对象和写入记录；存在状态时拒绝删除表，防止把可恢复任务当作普通结构回滚静默清除。

真实验证：

- 集成测试先用一套连接池创建待审批任务并关闭，再创建全新连接池和工作流，按相同 `run_id` 恢复并完成批准。
- 隔离测试库完成 `0006` 降级、重新升级和 `alembic check`，证明迁移可往返且元数据无漂移。
- 真实 Uvicorn 创建待审批任务后触发热重载，重载后 GET 仍返回 pending，审批后变为 completed；测试任务随后按精确 `run_id` 删除。
- 开发库迁移前后业务数据保持 7 个文档、6 个分块、6 个向量；清理冒烟任务后检查点状态表均为 0 行。

风险与后续：

- checkpointer 保存的是工作流执行状态，不自动提供满足业务合规要求的审批审计。后续仍需记录审批人、时间戳、操作原因和不可变事件。
- 当前没有保留期限和清理任务；长期运行需要按业务状态归档，并只清理已结束且超过保留期的线程。
- 严格固定包版本降低结构意外变化风险，但依赖升级必须同时维护 Alembic 迁移。

可能追问：

- 为什么不在每次启动时调用 `setup()`？
- 为什么 SQLAlchemy 使用 asyncpg，而 checkpointer 另建 psycopg 连接池？
- 检查点、业务运行表和审计日志有什么区别？
- 如何证明热重载后恢复的不是进程内缓存？
- 为什么 downgrade 在存在数据时选择失败，而不是自动删除？

## 下一阶段重点：结构化生成与业务工具

1. 选定文本生成模型，要求严格结构化输出、证据引用和失败降级，替换确定性生成器。
2. 设计只读 MES/QMS 工具协议、超时与错误分类，并先实现可测试的假工具。
3. 设计运行历史、审批人、时间戳和节点错误的独立审计查询能力。
4. 制定检查点归档和清理策略，再评估多 Worker 并发恢复与幂等副作用保护。

下一阶段应重点沉淀：结构化模型输出、引用约束、工具权限边界、业务审计与幂等执行。
