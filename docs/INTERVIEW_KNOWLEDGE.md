- 本文档跟随开发过程持续更新，不是项目完成后临时整理的背诵稿。

## 项目定位

QualityPilot 是面向 PCB 制造与 AOI 质量检测场景的质量异常分析和闭环处置智能体。目标流程是：

```text
异常输入
→ 意图识别与任务规划
→ 企业知识检索
→ 生产数据工具查询
→ 根因分析与证据汇总
→ 处置建议
→ 人工审批
→ 工单生成
→ 历史案例沉淀
```

项目重点不是普通聊天机器人，而是可追溯、可测试、可暂停恢复，并能安全调用业务工具的行业 Agent。

## 已沉淀的技术知识点

### 1. 健康检查与就绪检查的区别

当前实现分别提供：

- `/health`：只表示 FastAPI 进程能够响应。
- `/ready`：额外执行 `SELECT 1`，确认数据库连接可用。

面试表达：健康检查适合判断进程是否存活；就绪检查决定实例能否接收真实流量。数据库不可用时，进程可能仍然健康，但不应被认为已经就绪。

可能追问：

- 为什么不能只保留一个接口？
- 数据库查询超时时如何避免 readiness 长时间阻塞？
- Kubernetes 的 liveness、readiness 和 startup probe 应如何配置？

### 2. FastAPI lifespan 与资源管理

项目通过 lifespan 在启动时初始化数据库，在关闭时释放连接池。

设计价值：

- 把启动和关闭行为集中管理；
- 避免在模块导入阶段执行不可控的异步操作；
- 为后续模型客户端、任务队列和可观测性组件提供统一生命周期入口。

当前实现：应用启动时只执行数据库连接检查，表结构变更已交由 Alembic 管理，不再依赖 `create_all()` 修改现有数据库。

### 3. 异步 SQLAlchemy 会话

当前后端使用 `create_async_engine`、`async_sessionmaker` 和 FastAPI 依赖注入，为每个请求提供独立的 `AsyncSession`。

面试重点：

- 异步数据库访问避免请求线程在网络 I/O 时被阻塞；
- 每个请求拥有独立会话，路由层显式提交事务；
- `expire_on_commit=False` 便于提交后直接序列化 ORM 对象；
- `pool_pre_ping=True` 可以在取出连接时检查失效连接。

需要继续研究：事务边界、连接池大小、超时设置、并发写入冲突和异常后的 rollback。

### 4. PostgreSQL、pgvector 与数据建模

当前模型采用“文档主表 + 文档分块表”：

- 一个文档对应多个有序分块；
- `(document_id, chunk_index)` 保证同一文档内分块顺序不重复；
- 外键使用 `ON DELETE CASCADE`；
- `embedding` 当前允许为空。

为什么 Embedding 允许为空：新上传文档已经自动生成向量，但旧数据、人工创建的空文档以及失败后待重试的分块仍需要可空字段。单文档回填接口只处理空向量，允许分阶段完成历史数据向量化。

当前实际环境已验证：PostgreSQL 17.10、pgvector 0.8.6，两张知识库表存在，`embedding` 字段为可空的 `vector(1024)`。

### 5. 为什么需要 Alembic

`Base.metadata.create_all()` 只适合创建缺失表，不能可靠表达字段修改、约束变化、数据迁移和版本回退。

本阶段已经核对实际数据库结构，为现有两张表建立 `0001_existing_schema` 基线，并通过 `0002_file_ingestion` 只增加文件元数据和分块偏移字段。迁移前后原有记录保持一致，整个过程没有删除表、数据库或数据卷。

安全规则：不得执行 `docker compose down -v`，因为 `-v` 会删除 Compose 管理的数据卷。

### 9. 文件上传、解析、切分与事务一致性

本阶段采用分层实现：路由负责 HTTP 协议，导入服务负责大小限制和流程编排，解析器负责格式适配，切分器负责文本边界，文件存储服务负责生成安全名称和原子落盘。

关键设计与面试知识：

- 上传内容按块读取，累计超过 20 MB 立即返回 413，不能只信任请求头中的文件大小。
- 文件名会移除路径部分，存储时使用 UUID 名称，避免路径穿越、同名覆盖和用户文件名直接落盘。
- PDF 检查 `%PDF-` 签名，DOCX 检查 ZIP 签名，TXT/Markdown 拒绝 NUL 二进制内容。
- TXT/Markdown 支持 UTF-8 与 GB18030；PDF 和 DOCX 最终都转换成统一纯文本。
- PDF/DOCX 解析放入工作线程，避免 CPU/同步库阻塞 FastAPI 事件循环。
- 切分目标约 800 字符、重叠 100 字符，优先在中文句号、问号、分号和换行处结束。
- 每个分块记录 `chunk_index`、`char_start` 和 `char_end`，为引用溯源和后续评测保留依据。
- 文档元数据与全部分块放在一个数据库事务中；唯一约束故障测试证明分块失败时文档也会回滚。
- 原文件落盘不是数据库事务的一部分，因此数据库写入失败时必须执行补偿删除。
- SHA-256 用于内容追溯和后续重复检测，但当前没有直接把相同哈希设为唯一约束，因为同一文件可能需要以不同业务上下文重复导入。

真实验证：现有数据库完成纯增量迁移；当前 52 项自动化测试全部通过；真实 HTTP 上传 10,930 字节 TXT 后生成 9 个有序分块，测试数据和文件均已清理。

### 10. 云端 Embedding 选型、配置安全与真实 API 排障

业务问题：文本分块需要转换成固定维度向量，才能进行语义相似检索。

技术方案：选择阿里云百炼 `qwen3.7-text-embedding`，显式指定 1024 维，后续使用 pgvector 余弦距离检索。云端 API 避免了在开发机安装 Ollama 和维护本地模型，但引入网络依赖、调用成本和数据合规风险。

配置安全：

- API Key 仅保存在被 Git 忽略的 `backend/.env`，`.env.example` 只保留空占位符和公共默认值。
- Pydantic Settings 使用 `SecretStr | None`；普通打印只显示星号，同时允许健康检查和不调用模型的测试在无真实密钥环境运行。
- 维度、批量大小和超时时间使用有类型的配置字段与范围校验。

关键实现：

- 业务层依赖 `EmbeddingProvider` 协议，不直接依赖百炼客户端；工厂负责从 Settings 创建具体 Provider。
- 文档列表按配置的批量大小拆分请求，并根据响应 `index` 恢复输入顺序。
- 超时、网络异常和远端非成功状态分别映射为领域异常；网络异常、超时、429 与 5xx 使用可配置次数的指数退避重试，配置错误、4xx 参数错误和响应契约错误不重试。
- 响应在入库前校验数量、索引唯一性、1024 维约束以及 NaN/Infinity 等非法数值。
- 单元测试使用 `httpx.MockTransport`，验证 Provider 协议而不访问真实 API。

真实验证：专属 OpenAI 兼容端点返回 HTTP 200、1 条 1024 维向量和 38 Token 统计；`SecretStr` 打印为 `**********`。FastAPI 上传与回填通过假 Provider 验证实际 1024 维 PostgreSQL 写入，全量 52 项测试通过，`alembic check` 无结构差异。

排障过程：

1. Shell 未加载 `.env` 时，URL 展开后只剩 `/embeddings`，`curl` 返回 `No host part in the URL`；通过 `%q` 检查非敏感变量并重新加载绝对路径解决。
2. 环境变量正确后，WSL 默认 TLS 握手返回 `SSL_ERROR_SYSCALL`，说明请求尚未到达 HTTP 业务层。
3. 强制 IPv4 和 HTTP/1.1 后，专属 Host、公共 Host 和阿里云官网均完成 TLS，真实 Embedding 调用返回 200。因为两个参数同时引入，只能把原因收窄到 IPv6 网络路径或协议协商兼容性，不能无证据地宣称已精确定位。

测试取舍：普通单元测试不直接调用真实云 API，以避免网络不稳定、密钥泄露、费用和限流；后续应注入假 Provider，真实 API 仅用于显式启用的集成或冒烟测试。

当前风险：

- 当前自动重试发生在同步 HTTP 请求内，可能增加响应时间；大规模回填仍需要持久化任务队列、任务状态、限流和可观测性。
- 云端调用需要考虑网络、限流、配额、脱敏、可观测性和降级策略。

### 11. 向量维度增量迁移与数据保护

业务问题：模型输出固定为 1024 维，但早期数据库字段定义为 `vector(1536)`。ORM 类型与实际数据库类型不一致会阻止正确入库，也会让后续索引和距离计算建立在错误结构上。

实施过程：

- 迁移前先只读检查实际数据库，确认 Alembic 位于 `0002_file_ingestion`，数据库有 1 条原有文档、0 条分块、0 条非空向量。
- ORM 的字段类型由 `Vector(1536)` 调整为 `Vector(1024)`，新增 `0003_embedding_1024` 增量迁移，没有删除或重建数据库、表和数据卷。
- 迁移脚本在修改类型前显式检查是否存在非空向量；如果存在则抛出异常，要求先设计重新嵌入或数据搬迁方案，避免数据库隐式转换造成不可逆的数据问题。
- downgrade 同样只允许在向量全部为空时执行，因为 1024 维向量不能直接变回有业务意义的 1536 维向量。
- 应用前检查了离线 SQL，确认只包含前置条件、字段类型变更和 Alembic 版本更新。

真实验证：迁移已在现有数据库升级到 `0003_embedding_1024`，字段类型为可空的 `vector(1024)`，原有 1 条文档记录保持不变。随后在显式事务中写入一条 1024 维临时向量，通过 `vector_dims` 验证维度后回滚，确认没有测试分块残留。`alembic check` 无待生成操作，当前全量 52 项自动化测试全部通过。

面试表达：数据库迁移不是简单修改 Python 类。应先调查真实数据，再通过版本化迁移表达结构变化；对可能损坏数据的类型变更增加可执行的前置条件，并分别验证迁移 SQL、真实升级、数据保留、目标类型写入和应用回归。

### 12. 上传自动向量化、重试与幂等回填

业务问题：仅有 Provider 和向量字段还不能形成可检索知识库。新上传分块需要自动写入向量，历史空向量需要可重复执行的回填入口，同时外部模型故障不能造成文件、文档或部分分块残留。

关键设计：

- 上传流程按“读取与解析 → 切分 → 云端向量化 → 原文件落盘 → 文档、分块和向量单事务写入”执行。云端调用位于数据库事务之前，避免在网络等待期间占用长事务。
- Provider 通过 FastAPI 依赖注入的是惰性工厂；格式或大小校验失败时不会创建客户端，测试可以替换为假 Provider。
- 网络错误、超时、429 和 5xx 按配置进行指数退避重试；不可重试错误立即失败。Provider 无论成功失败都会关闭自有 HTTP 客户端。
- 回填接口先查询目标并结束只读事务，只对 `embedding IS NULL` 的分块调用模型。写回再次附加 `embedding IS NULL` 条件，重复调用直接跳过已完成分块，并避免并发请求覆盖已有结果。
- 分块查询只返回 `has_embedding` 和 `embedding_dimension`，不把 1024 个浮点数直接暴露给前端。
- 上传向量失败返回 502 或 503；由于向量化发生在文件保存和数据库事务之前，不会留下文件、文档或部分分块。

事务边界取舍：外部 API 无法加入 PostgreSQL 的 ACID 事务。本阶段选择先完成外部计算、再进行本地原子写入，获得简单明确的失败语义；代价是数据库最终写入失败时已经消耗了模型额度。生产级异步方案应使用任务表、幂等键、状态机和持久化重试队列。

真实验证：假 Provider 生成 1024 维向量后，上传接口把全部向量写入实际 PostgreSQL；分块查询返回维度 1024。历史回填首次写入 2 个分块，第二次返回写入 0、跳过 2，Provider 总共只调用一次。模拟网络故障连续失败时按配置调用 3 次，接口返回 503，数据库没有生成失败文档。全量 52 项测试通过，测试未访问真实百炼 API、未消耗 Token。

### 13. 余弦检索、HNSW 索引与引用结果

业务问题：向量写入数据库后，还需要把用户问题转换为同模型向量，按照语义接近程度检索分块，并返回足够的来源信息供后续 Agent 引用和人工核查。

关键实现：

- 新增 `POST /api/v1/knowledge/search`，请求包含去除首尾空白后的查询文本和 1—50 范围内的 `top_k`。
- 空知识库先执行非空向量存在性检查并直接返回空列表，不创建 Provider、不访问云端，也不消耗 Token。
- 非空知识库调用与文档相同的 Provider 生成查询向量，并复用超时、网络、429 和 5xx 重试策略。
- SQLAlchemy 使用 pgvector 的 `cosine_distance`，实际 SQL 运算符为 `<=>`；按距离升序取 Top-K，并用 `1 - cosine_distance` 返回余弦相似度。
- 结果不只返回正文，还包含 `chunk_id`、`document_id`、标题、来源类型、来源 URI、原文件名、分块序号和字符起止位置，为后续引用溯源保留证据。
- `0004_embedding_hnsw` 迁移创建只覆盖非空向量的 HNSW 索引，操作符类使用与余弦查询一致的 `vector_cosine_ops`。

索引取舍：HNSW 查询性能和召回表现通常优于精确全表扫描，但索引会增加内存、磁盘和写入成本，并且属于近似检索。当前先使用 pgvector 默认 HNSW 参数，不能在没有真实规模数据和评测集时编造性能提升或召回率。

真实验证：在实际 PostgreSQL 中插入三条 1024 维测试向量，查询向量与它们的余弦相似度分别为 1、0.8 和 0，接口按预期返回前两条，并正确携带文档来源与字符偏移。另在显式事务中插入 200 条临时非零向量，关闭顺序扫描后执行 `EXPLAIN`，查询计划显示 `Index Scan using ix_knowledge_document_chunks_embedding_hnsw_cosine`，随后事务整体回滚。当前全量 52 项测试通过，没有调用真实百炼 API。

重要边界：本次 `EXPLAIN` 只证明 SQL 形态能够使用索引，不等于生产数据规模下必然更快。后续必须用真实数据量执行 `EXPLAIN ANALYZE`，比较延迟、索引体积、构建时间和 Recall@K。

### 14. 检索评测集与质量指标

业务问题：只实现向量检索无法证明搜索质量。没有固定查询和相关性标注时，修改模型、切分、索引或排序策略后只能依赖主观感受，无法判断是否回退。

关键实现：

- 建立第一版合成脱敏 PCB/SOP 数据集，包含 5 份 Markdown 文档、8 条查询、稳定文档编号、相关文档标注和证据短语。
- Pydantic 在运行前校验文档编号、标题和查询编号唯一，并拒绝引用未知文档或空证据。
- 评测运行器逐条调用现有搜索 API，根据唯一标题映射稳定文档编号，不自动上传或删除数据。
- 指标模块与真实 HTTP 调用解耦，可以用固定命中结果做确定性单元测试。
- JSON 报告保留总体指标和逐查询结果，便于后续向量检索、全文检索、融合排序和 Rerank 使用同一基准比较。

指标定义：

- 文档级 Recall@K：Top-K 分块覆盖的相关文档去重数量除以标注相关文档总数。
- MRR：每条查询第一个相关分块排名的倒数，再对全部查询取宏平均。
- 引用正确率@K：命中分块必须来自相关文档，并包含该文档至少一个标注证据短语；先按查询计算正确分块占返回分块比例，再取宏平均。这是本项目的证据约束指标，不应冒充通用行业标准。

为什么先评测再做 BM25：固定基线可以证明后续改动带来的真实增益，也能暴露语义召回、精确术语匹配和引用证据之间的不同问题。

真实验证：经用户明确授权，通过真实 Uvicorn 上传接口导入 5 份合成文档，生成 5 个分块，并由 `vector_dims` 确认每个向量均为 1024 维。

真实百炼基线结果：Top-1 的 Recall、MRR、引用正确率均为 0.8750；Top-3 的 Recall 为 0.9375、MRR 为 0.9167、引用正确率为 0.3333。Q001—Q007 的正确文档均排第 1；Q008 要求两个相关文档，Top-3 只召回其中一个且排第 3。Top-3 引用正确率较低也受指标分母影响：多数查询只有一个相关分块，但固定返回三条，因此即使第一条正确也只有 1/3。

故障排查：首次运行 Top-1 时，前两条查询成功，第三条在后端 Provider 重试耗尽后返回 503，原评测运行器直接终止且不生成报告。随后为评测 HTTP 客户端增加有限指数退避，只重试网络错误、429 和 5xx，普通 4xx 不重试，并增加模拟 503 后成功的测试；重新运行后报告完整生成。

当前全量 52 项测试通过，`alembic check` 无结构差异。向量、关键词和混合检索逐查询报告均已保存；真实向量调用没有汇总 Token 用量，因此不编造成本数字。

风险和不足：

- 当前样例规模小且为合成数据，只适合开发回归，不能代表生产效果。
- 运行器按唯一标题把 API 结果映射到稳定编号；后续应在文档元数据中增加专门的数据集标识，避免同名文档干扰。
- 证据短语匹配是可解释的确定性检查，但无法识别同义改写，后续可以增加人工复核或独立评判模型。

- Recall@K、Precision@K 和 MRR 分别回答什么问题？
- 为什么评测相关性使用文档级标注，而检索返回的是分块？
- 为什么合成数据不能当成简历中的生产指标？
- 如何保证引入 BM25 或 Rerank 后的对比公平？

### 16. 中文关键词检索与 RRF 混合排序

业务问题：纯向量检索擅长语义相似，但对设备代码、缺陷名称、工艺参数等精确术语可能不稳定；只做关键词检索又难以覆盖同义表达。两种信号需要在保持来源可追踪的前提下组合。

技术方案：

- 第一版中文关键词检索选择 PostgreSQL 官方 `pg_trgm` 扩展，而不是直接使用内置英文导向的 `to_tsvector`。trigram 按字符片段计算相似性，无需额外中文分词服务，能覆盖中文短语、英文缩写和设备代码。
- `0005_trigram_search` 安装扩展并在分块正文创建 `gist_trgm_ops` 索引；查询使用 `<->>` word-similarity 距离进行 KNN 排序，并过滤完全没有字符片段重叠的结果。
- 搜索请求新增 `vector`、`keyword`、`hybrid` 三种模式，默认仍为 `vector`，保持旧客户端和已保存向量基线可复现。
- 返回值保留 `match_type`、`vector_score` 和 `keyword_score`，避免只有一个无法解释的综合分数。

为什么使用 RRF：余弦相似度与 trigram word similarity 的分布和量纲不同，直接相加需要脆弱的归一化与权重。Reciprocal Rank Fusion 只依赖各通道排名：每个候选累加 `1 / (rrf_k + rank)`，再按融合分数排序。本项目默认各通道等权、候选倍率 5、`rrf_k=60`，参数由 Pydantic Settings 校验。

索引排障：首次 EXPLAIN 仍然是顺序扫描。原因是 SQLAlchemy `CAST(distance AS FLOAT)` 改变了 ORDER BY 表达式，加上 UUID 次级排序后不再满足 GiST KNN 排序形式。改用只影响 Python 类型、不生成 SQL CAST 的 `type_coerce`，并移除次级排序后，计划变为 `Index Scan using ix_knowledge_document_chunks_content_gist_trgm`。事务内 200 条临时数据随后全部回滚。

真实同集评测：

- 向量 Top-1：Recall 0.8750、MRR 0.8750、引用正确率 0.8750。
- 关键词 Top-1：Recall 0.6875、MRR 0.7500、引用正确率 0.7500。
- 混合 Top-1：Recall 0.9375、MRR 1.0000、引用正确率 1.0000。
- 向量 Top-3：Recall 0.9375、MRR 0.9167、引用正确率 0.3333。
- 关键词 Top-3：Recall 1.0000、MRR 0.8750、引用正确率 0.5625。
- 混合 Top-3：Recall 1.0000、MRR 1.0000、引用正确率 0.3750。

结果解释：关键词 Top-1 弱于向量，但扩大候选后能补齐向量漏掉的相关文档；RRF 把互补候选提前，使混合 Top-1 三项指标均提升。Top-3 引用正确率仍受固定返回三条、每个查询通常只有一条证据分块的指标定义影响。

风险和不足：

- 评测只有 5 份合成文档和 8 条查询，提升只能作为开发基线，不能写成生产准确率。
- `pg_trgm` 是字符相似性，不理解词义，也不是 BM25；长文本、同义词和完全不同字面的表达仍依赖向量通道。
- 当前融合是固定等权 RRF；是否增加加权、Rerank 或中文分词必须由更大真实评测集决定。
- 混合模式需要调用云端查询 Embedding，网络失败语义与向量模式一致；关键词模式可作为不依赖云端的显式调用方式。

- 为什么不能直接把余弦相似度和关键词分数相加？
- RRF 的 `rrf_k` 和候选集大小分别如何影响排序？
- `type_coerce` 与 SQL `CAST` 为什么会产生不同查询计划？

### 17. LangGraph 状态机、人工审批与运行时依赖

业务问题：质量处置 Agent 不能把“检索到证据”和“已经批准执行”混为一谈。流程必须保留证据、草稿和审批结果，并能在等待工程师判断时暂停。

关键实现：

- `POST /api/v1/agent/runs` 创建 UUID `run_id`，执行知识检索和证据草稿节点，然后在审批节点暂停并返回 202。
- `GET /api/v1/agent/runs/{run_id}` 查询证据、草稿、状态和审批结果。
- `POST /api/v1/agent/runs/{run_id}/approval` 恢复同一工作流；批准后才产生最终响应，拒绝后最终响应为空，重复审批返回 409。
- Agent 默认使用 hybrid 检索，也允许 vector 或 keyword，并保留文档、分块、来源和通道分数。
- 第一版生成器不调用大模型，只按确定性规则整理证据并附加风险提示。

状态设计：

- LangGraph 状态只包含 `run_id`、问题、检索模式、证据、草稿、状态和审批结果等可序列化数据。
- `AsyncSession`、Provider 工厂、检索器和生成器通过 `Runtime Context` 注入节点，不写入检查点。
- 审批节点使用 `interrupt` 暂停；恢复时以 `run_id` 作为 `thread_id`，通过 `Command(resume=...)` 注入审批结果。
- interrupt 所在节点恢复时会从节点开头重新执行，因此中断前不能放置发送工单、扣费等非幂等副作用。

边界与取舍：

- 第一版曾使用 `InMemorySaver` 验证流程语义；现已换成 PostgreSQL 检查点，内存实现只保留为工作流单元测试默认值。
- 检查点解决工作流恢复，不等于完整业务审计；后续已增加独立审批事件，但可信身份、节点错误历史和保留期限仍未完成。
- 批准当前只发布最终响应，不调用 MES/QMS、不生成真实工单。
- 外部检索或 Embedding 异常沿用现有 HTTP 错误映射；持久失败状态、重试历史和审计日志仍待实现。

真实验证：Agent 流程测试覆盖暂停恢复、批准拒绝、重复审批冲突、缺失运行记录、请求校验、关键词模式不调用 Embedding 和混合检索路径。运行中的 Uvicorn 完成关键词模式启动、状态查询和批准恢复，依次返回 202、200、200，检索 3 条证据并进入 completed；该冒烟未调用云端。

### 18. PostgreSQL 持久化检查点与进程恢复

业务问题：人工审批可能等待数小时。检查点若只在内存中，服务重启、热重载或多 Worker 切换都会使待审批任务消失，因此 API 不能可靠地按 `run_id` 恢复。

关键实现：

- 使用 `AsyncPostgresSaver` 保存 LangGraph 状态，FastAPI lifespan 在启动时打开 psycopg 异步连接池，在关闭时释放连接。
- SQLAlchemy 继续通过 asyncpg 处理业务 ORM；checkpointer 使用 psycopg，因为官方实现依赖 psycopg 的连接、行工厂和 pipeline 能力。两个连接池访问同一个 PostgreSQL，但生命周期和职责分离。
- 状态序列化显式使用 `JsonPlusSerializer(allowed_msgpack_modules=None)`，不允许环境变量扩大可反序列化模块范围。
- 连接池启用 `autocommit=True`、`dict_row` 和 `prepare_threshold=0`；最小、最大连接数由 Pydantic Settings 校验。

迁移所有权：

- 没有在应用启动时调用 checkpointer 的 `setup()`，因为项目约定所有数据库结构变更都必须经过 Alembic 审查。
- `0006_agent_checkpoints` 按当前固定版本 `langgraph-checkpoint-postgres==3.1.1` 建立官方检查点结构和迁移版本记录。
- Alembic 元数据登记同一结构，使 `alembic check` 能识别真实漂移；未来升级包版本时必须先比较其迁移定义，再新增项目迁移。
- downgrade 会先统计检查点、二进制对象和写入记录；存在状态时拒绝删除表，防止把可恢复任务当作普通结构回滚静默清除。

真实验证：

- 集成测试先用一套连接池创建待审批任务并关闭，再创建全新连接池和工作流，按相同 `run_id` 恢复并完成批准。
- 隔离测试库完成 `0006` 降级、重新升级和 `alembic check`，证明迁移可往返且元数据无漂移。
- 真实 Uvicorn 创建待审批任务后触发热重载，重载后 GET 仍返回 pending，审批后变为 completed；测试任务随后按精确 `run_id` 删除。

### 19. 结构化文本生成、证据引用与安全降级

业务问题：确定性模板只能整理证据，无法形成针对具体问题的分析；直接采用大模型自由文本又会带来字段漂移、虚构来源、提示注入和远端服务失败等风险。生成结果还必须继续受人工审批约束。

关键实现：

- 默认选用百炼固定快照 `qwen3.7-max-2026-05-20`，优先使用 2026-08-20 到期的免费额度；复用现有 `DASHSCOPE_API_KEY`，但为文本生成独立配置 Base URL、模型、超时、重试和最大输出长度。
- 通过 OpenAI 兼容 Chat Completions 调用，设置 `response_format={"type":"json_object"}`、`enable_thinking=false`，并在系统提示中明确要求只输出 JSON。
- 模型输出只允许 `summary`、`suggested_actions`、`risk_notes` 和 `citations` 四个字段；Pydantic 拒绝额外字段、空摘要、空风险、过长字符串和非法类型。
- 每条检索证据在提示词中获得从 1 开始的临时编号。模型只能返回编号，服务端去重、检查范围，再映射成真实 `chunk_id`；越界引用会使整个模型响应失效。
- 知识库分块被明确视为不可信数据，系统提示要求忽略其中的指令，降低文档提示注入影响。
- 网络错误、超时、429 和 5xx 使用有限指数退避；缺少配置、响应违约或重试耗尽时，返回确定性草稿，并用 `generation_mode=deterministic_fallback` 与风险说明显式暴露降级。
- 空证据直接返回“证据不足”草稿，不创建客户端、不调用云端。无论模型生成还是降级草稿，都停在原有人工审批节点。

设计取舍：JSON Mode 只保证输出为 JSON，不等于符合业务契约，所以仍需本地强校验。引用采用服务端映射而不是让模型返回 UUID，避免模型伪造来源，同时减少提示词和输出长度。生成失败选择可见降级，是为了保持待审批流程可用；降级结果不能伪装成模型分析。

真实验证：使用 `httpx.MockTransport` 验证了请求参数、结构化响应、引用映射与去重、越界引用拒绝、连续三次 503 后降级、缺少 API Key 降级和空证据短路。58 项非集成测试通过；隔离 PostgreSQL 从 `0001` 升级至 `0006` 后 67 项完整测试通过。

真实百炼冒烟：启动 Uvicorn 后使用 keyword 模式提问“AOI 发现桥接应该如何处理？”，`qwen-plus` 返回结构化摘要、5 条建议、3 条风险和 3 个候选证据引用，服务端校验后 `generation_mode=model` 并进入待审批。批准后状态变为 `completed`，最终响应与审批草稿一致。冒烟只读取知识库；随后按精确 `run_id` 在单事务中删除 22 条 checkpoint writes、5 条 blobs 和 6 条 checkpoints，并确认知识库仍为 7 个文档、6 个分块、6 个向量。当前实现未记录生成 usage，因此不声称本次 Token 用量或成本。

免费模型切换验证：本地 `.env`、默认 Settings 和 `.env.example` 改为 `qwen3.7-max-2026-05-20` 后，使用同一 keyword 问题再次真实调用。模型返回结构化摘要、4 条建议、4 条风险和全部 3 个候选分块引用，`generation_mode=model`，没有触发确定性降级；批准恢复后状态为 `completed`。随后精确清理该 `run_id` 的 22 条 writes、5 条 blobs 和 6 条 checkpoints，并再次确认知识库为 7 个文档、6 个分块、6 个向量。

风险和不足：

- JSON Mode 不是服务端 JSON Schema 强约束；当前安全性依赖提示约束与本地 Pydantic 校验。
- 引用校验只能证明引用来自候选证据，不能自动证明结论确实被该证据支持；后续需要评测集和人工审查。
- 当前降级原因记录在草稿风险说明中，还没有独立的节点错误历史、指标和告警。
- 已完成一次真实模型端到端冒烟，但还没有针对提示注入、引用忠实度和生成质量建立系统评测集。

### 20. MES/QMS 只读工具协议与故障隔离

业务问题：质量分析最终需要结合批次、设备、检验和不合格事件等实时业务数据，但 Agent 不能因为“需要查询”就获得创建工单、修改状态或调整生产参数的权限。不同系统的网络、认证和响应质量也不能互相拖垮。

关键实现：

- 定义 `ReadOnlyBusinessTool` 协议，只包含工具名称、系统类型和 `query`；协议中没有 write、execute、create 或 update 方法，从类型边界限制能力。
- MES/QMS 记录使用统一 `BusinessRecord`，包含来源系统、稳定记录 ID、类型、摘要和受限的标量属性。
- `collect_business_context` 并发调用多个工具，但保持配置顺序返回结果，便于稳定测试和后续提示词构造。
- 每个工具使用独立超时；一个 MES 查询超时只产生该工具的失败结果，不会丢弃已成功返回的 QMS 数据。
- 错误分类包含 timeout、authentication、permission、unavailable、invalid_response 和 unexpected，并标记是否适合重试。
- 返回结果需要满足数量上限、来源系统一致和记录 ID 唯一；违反适配器契约时整组结果按 `invalid_response` 拒绝。
- 未知异常不向调用方传播原始文本，避免连接串、凭据或供应商内部错误泄露。
- `InMemoryReadOnlyBusinessTool` 提供可控响应、延迟和错误注入，只用于测试与本地演示，不冒充真实 MES/QMS。

设计取舍：只读与写入使用能力分离，而不是依靠提示词要求模型“不要写”。并发查询提升多系统聚合效率，但必须采用每工具超时与部分成功语义，否则一个慢系统会阻塞全部上下文。第一阶段先验证协议和错误边界，随后再用受限 DTO 接入 Agent，避免直接固化供应商原始响应。

真实验证：新增 8 项测试，覆盖 MES/QMS 同时成功、顺序稳定、单工具超时而另一工具成功、认证与暂不可用错误分类、跨系统记录拒绝、未知错误信息脱敏、非法查询参数和重复工具名。当前 66 项非集成测试通过；隔离 PostgreSQL 从 `0001` 至 `0006` 迁移后 75 项完整测试通过，`alembic check` 无结构漂移，`pip check` 无依赖冲突。

风险和不足：

- 当前只有协议、执行器和内存假工具，没有真实 MES/QMS 认证、字段映射或网络适配器。
- 工具结果现已通过受限 DTO 进入 LangGraph 状态、生成提示词和审批 API，但真实适配器仍需确定逐字段持久化白名单。
- 当前只分类是否可重试，尚未实现工具级重试、熔断、指标和告警。
- 即使未来增加写工具，也必须使用独立权限、审批、幂等键和审计事件，不能扩展当前只读协议绕过边界。

可能追问：

- 如何让一个业务系统超时但保留另一个系统的结果？

### 21. 只读业务上下文进入 LangGraph 与结构化生成

业务问题：工具协议本身不能产生可用的 Agent 能力。MES/QMS 查询结果还要安全地进入可恢复状态、模型提示和审批接口，同时允许部分系统失败，并避免把连接对象、凭据或任意供应商响应写入 PostgreSQL 检查点。

关键实现：

- 在知识检索和草稿生成之间增加 `query_business_context` 节点；节点并发调用运行时注入的只读工具，把成功记录和失败结果分别写入状态。
- 工具对象保留在 runtime context。状态中只保存纯字典、列表和标量 DTO，因此 PostgreSQL checkpointer 不需要序列化适配器或连接。
- `BusinessRecord` 限制摘要长度、最多 20 个属性、属性名和字符串长度，并拒绝嵌套对象及非有限浮点数；转换时把 Enum 和 Mapping 复制为稳定的普通值。
- 模型提示同时提供知识证据、只读业务记录和工具故障，并把三者都标记为不可信输入。模型只返回证据编号和业务编号，服务端分别校验范围后映射到分块 UUID 与 `tool_name + record_id`。
- 确定性降级也能利用业务记录；当一个工具失败时，成功记录仍用于草稿，失败分类进入风险说明。没有知识和业务记录时不会创建模型客户端。
- API 返回业务记录、工具故障和草稿中的复合业务引用；新增字段带默认空列表，以兼容本功能上线前保存的检查点。

为什么使用复合业务引用：真实 MES 与 QMS 可能都存在 `12345` 这样的记录 ID，只返回 `record_id` 会产生歧义。`tool_name + record_id` 同时标识适配器边界和源记录，也便于未来审计具体由哪个连接器提供数据。

安全边界：当前默认工具集合为空，没有真实 MES/QMS 连接，也不存在写方法。DTO 的通用标量限制只是第二道防线；真实适配器接入时仍必须逐字段映射允许持久化的业务数据，不能把原始供应商 JSON 整包写入检查点或提示词。

真实验证：20 项定向测试覆盖并发业务查询、部分失败、DTO 转换、结构化模型引用、业务记录单独生成、工作流和 API 返回。完整非集成测试为 69 项通过、9 项排除；隔离 PostgreSQL 上 78 项全部通过，持久化测试确认业务记录可跨连接池恢复。`compileall`、`pip check` 和 `alembic check` 均通过。测试使用内存假工具和 `httpx.MockTransport`，没有连接真实 MES/QMS，也没有调用百炼文本模型。

风险和后续：

- 通用 DTO 尚未等于真实系统字段白名单；每个生产适配器都需要单独的数据最小化审查。
- 工具失败目前进入工作流状态和响应；独立不可变事件当前只覆盖审批决策，尚未覆盖工具错误、指标、告警、重试或熔断。
- 检查点保障恢复，不负责业务记录的新鲜度；后续需要查询时间、源版本和过期策略。
- 未来写操作必须使用独立协议、最小权限、审批人身份、幂等键和 outbox，不能复用只读工具接口。

### 22. 幂等审批决策与不可变审计事件

业务问题：LangGraph 检查点能恢复流程，却不能回答“谁在何时提交了什么决策”，也不能阻止历史记录被普通更新覆盖。审批接口还可能因超时重试或并发请求重复恢复工作流。

关键实现：

- `0007_agent_audit_events` 新增独立表，记录事件 UUID、Agent 运行 UUID、固定事件类型、提交者标识、批准或拒绝、备注和数据库生成时间。
- `(run_id, event_type)` 唯一约束保证一个运行只有一个审批决策，事件 UUID 同时作为客户端可提供的 `request_id`。
- 相同请求 ID 和完全相同载荷再次提交时返回同一结果；请求 ID、提交者、决策或备注任一不同都会返回 409，避免把冲突伪装成重试。
- 审批事件先提交，再恢复 LangGraph。事件是审批事实，工作流状态是可重建投影；若恢复阶段中断，调用方可用原请求 ID 重放。
- PostgreSQL statement trigger 拒绝 `UPDATE`、`DELETE` 和 `TRUNCATE`；`0007` 降级检测到任何审计记录时也会拒绝删除表。
- `GET /api/v1/agent/runs/{run_id}/audit-events` 独立查询审批历史，常规运行查询也返回对应的 `approval_event`。

兼容与身份边界：旧客户端不传新增字段仍可审批，服务端会生成请求 ID，并把提交者明确记录为 `unverified`。请求体里的 `actor_id` 只是客户端声明，不是经过认证的身份；后续接入 OIDC/JWT 时应由服务端从可信主体填充并忽略请求体身份。

一致性取舍：SQLAlchemy 审计事务与 LangGraph psycopg 检查点事务无法组成一个本地数据库事务。选择“事实先落库、投影后更新”可以保证审批不丢失，并允许幂等恢复；代价是极短时间内可能出现事件已存在而工作流仍待审批，后续应增加自动对账和投影恢复任务。

真实验证：隔离 PostgreSQL 从完整迁移链升级到 `0007`，81 项测试全部通过。测试覆盖 SQL 存储创建与幂等读取、不同决策冲突、真实 API 到 PostgreSQL 的依赖接线，以及数据库对 UPDATE、DELETE、TRUNCATE 的拒绝。`alembic check` 无漂移，`pip check` 正常。开发库增量升级后仍为 7 个文档、6 个分块、0 条检查点，审计表初始为 0 行。

风险和后续：

- `actor_id` 未经过身份认证，不能作为不可抵赖证据。
- 当前只记录最终审批决策，不记录查看草稿、重复冲突、工具失败等完整操作轨迹。
- 防篡改触发器保护常规 DML，但数据库所有者仍可移除触发器；更高合规要求需要独立审计账号、权限隔离、外部归档或签名链。
- 尚无事件归档、保留期限和 LangGraph 投影自动对账任务。

### 23. API Key 摘要认证、角色授权与身份来源

业务问题：不可变审计只能证明“某个字符串被记录”，不能证明请求者确实拥有该身份。如果继续信任请求体 `actor_id`，客户端可以直接冒充工程师；同时又要避免在配置文件中保存可直接使用的原始密钥。

关键实现：

- 服务端配置 `AGENT_APPROVAL_API_KEY_SHA256`、`AGENT_APPROVAL_ACTOR_ID` 和强制开关，只保存 64 位 SHA-256 摘要与服务端身份映射。
- 客户端通过 `Authorization: Bearer <api-key>` 提交原始随机 Key；服务端计算 SHA-256，并使用 `hmac.compare_digest` 做常量时间比较。
- 认证成功产生不可变 `ApprovalPrincipal`，带有服务端 actor、`quality_approver` 角色和 `api_key_sha256` 认证方式。审批路由忽略请求体身份，使用 principal 身份写审计。
- 已认证但没有审批角色的主体返回 403；强制模式下缺少、格式错误或不匹配的凭据返回 401 和 `WWW-Authenticate: Bearer`。
- `0008_audit_actor_auth` 为审计表增加认证布尔值和认证方式，检查约束要求已认证事件必须有认证方式、未认证事件不得伪造认证方式。
- 默认强制开关为 false，保持现有本地调用兼容；未认证事件继续保存客户端声明，但 `actor_authenticated=false`、`auth_method=null`，不会与可信身份混淆。

为什么保存摘要：数据库或环境配置泄露时，摘要不能直接作为 Bearer 凭据使用。比较过程采用常量时间函数，避免普通字符串比较过早返回。由于 API Key 仍可能被暴力猜测，客户端必须使用足够长的随机值，而不是人类口令。

身份防冒用：测试让已认证 principal 为 `verified-engineer-001`，请求体故意声明 `spoofed-client-identity`；最终审计只记录服务端身份。角色为空的已认证主体在审计事件写入前即被拒绝。

真实验证：认证与审批 API 定向测试 10 项通过；隔离 PostgreSQL 完整回归 89 项通过，其中非集成 77 项、集成 12 项。测试覆盖配置缺失、摘要格式、Bearer 格式、错误 Key、常量时间摘要匹配、身份覆盖、角色拒绝、数据库认证来源约束和未认证兼容路径。`0008` 应用到开发库后，7 个文档、6 个分块、0 条检查点和 0 条审计事件保持不变。

风险和后续：

- 当前只有一个配置身份，不适合多人审批、人员离职撤权或角色动态管理。
- SHA-256 摘要方案不携带签发者、受众、过期时间和会话上下文；下一步应接入 OIDC/JWT 并校验 issuer、audience、expiry 和 subject。
- 尚无双 Key 轮换窗口、密钥 ID、撤销和认证失败安全指标。
- 默认兼容模式不是生产安全默认值；生产部署必须显式开启强制认证并配置高熵 Key 摘要。

### 24. 节点错误历史、脱敏分类与故障追踪

业务问题：HTTP 503 只能说明本次请求失败，无法回答失败属于哪个 Agent 节点、是否适合重试，也无法在服务重启后查询。直接保存异常字符串又可能把内部 Host、令牌或供应商响应写入数据库。

关键实现：

- 检索、业务上下文和草稿节点捕获普通异常并抛出 `AgentNodeExecutionError`，只附加 `retrieval`、`business_context` 或 `drafting` 阶段，原异常保留为内部 cause。
- API 边界使用白名单分类器把已知 Embedding 异常映射为 configuration、timeout、transport、api、response；未知异常统一为 unexpected。
- 分类器生成固定公开消息和 retryable 标记，从不复制原异常文本。测试异常中故意包含内部 Host 和 token，HTTP 响应及错误查询均没有泄露。
- `0009_agent_run_errors` 新增独立追加式错误表和运行 ID、时间索引；数据库触发器拒绝 UPDATE、DELETE、TRUNCATE，存在记录时迁移降级拒绝删表。
- 启动失败通过 `X-Agent-Run-Id` 返回追踪 ID，并在 CORS 中暴露；调用方随后可查询 `/api/v1/agent/runs/{run_id}/errors`。
- SQL 错误存储在追加前回滚当前会话，确保检索 SQL 使事务失败时仍有机会开启新事务写入错误事件。

错误语义边界：单个 MES/QMS 工具超时已经是允许部分成功的结构化结果，不属于工作流中断；文本生成服务失败会降级为确定性草稿，也不属于中断。只有使图执行无法继续的异常进入运行错误表，避免同一故障在多个通道重复计数。

为什么在 API 边界分类：节点负责业务编排，不应了解 HTTP 状态和公开错误文案。边界层同时拥有运行 ID、错误存储和 HTTP 映射，适合统一完成脱敏、持久化与响应；内部 cause 仍可供受控日志或调试使用。

真实验证：节点错误阶段和 API 定向测试 13 项通过；隔离 PostgreSQL 完整回归达到 100 项，其中非集成 86 项、集成 14 项。测试覆盖三类节点阶段、六类错误映射、原文脱敏、retryable、真实 SQL 追加查询以及 UPDATE/DELETE/TRUNCATE 防篡改。开发库升级到 `0009` 后保持 7 个文档、6 个分块、0 条检查点和 0 条审批事件，新错误表为 0 行。

风险和后续：

- PostgreSQL 自身不可用时，错误事件写入也可能失败；当前保证不覆盖原业务错误，但需要外部日志或遥测补足。
- 当前错误历史没有 acknowledged、resolved、重试次数和关联外部请求 ID。
- 只有启动工作流节点纳入记录，审批恢复阶段的未知 checkpointer 故障尚未建立同样的持久化恢复策略。
- 查询接口尚未分页，长期保留需要归档和清理策略。

### 25. 时间窗口运行指标与阈值告警快照

业务问题：逐条错误历史适合排障，却不能快速回答“最近 24 小时有多少失败、影响多少运行、集中在哪个节点、认证审批覆盖率如何”。如果为每次请求手工更新计数器，又会引入事件已经落库但计数器更新失败的双写漂移。

关键实现：

- `GET /api/v1/agent/metrics` 接受 1—720 小时窗口，以一次生成时间计算统一窗口起点。
- 直接聚合不可变的 `agent_audit_events` 和 `agent_run_error_events`，统计审批总数、认证审批、批准/拒绝、错误总数、受影响运行、可重试错误、阶段分布和类型分布。
- 阶段与类型使用数据库 `GROUP BY`；受影响运行使用 distinct run ID；多个条件计数在同一聚合查询中使用 SQL FILTER，减少往返。
- `AGENT_ERROR_ALERT_THRESHOLD` 由 Settings 限制在 1—10000；窗口内错误数达到阈值时返回 `warning`，否则为 `ok`。
- 响应只包含时间、阈值和聚合数字，不返回 actor、问题、审批备注、业务记录或错误消息。

为什么直接聚合事件：审批和错误表已经是不可变事实来源，实时聚合没有额外双写一致性问题。当前数据规模很小，四条聚合 SQL 的复杂度和延迟可接受；数据增长后可按小时建立增量汇总或导出到时序系统。

测试方法：API 测试注入假指标存储，验证窗口参数、阈值传递、响应结构和敏感字段缺失；PostgreSQL 测试先读取基线，再新增一条已认证审批和两条不同阶段错误，用前后差值验证全部计数及 warning 边界，避免测试历史数据导致脆弱断言。

真实验证：完整测试达到 102 项，其中非集成 87 项、PostgreSQL 集成 15 项；`alembic check` 无漂移，`pip check` 正常。本阶段没有数据库迁移，也没有调用百炼、MES 或 QMS。随后启动真实 Uvicorn 请求 24 小时指标窗口，HTTP 200 返回审批、错误和受影响运行均为 0，`alert_status=ok`、阈值 5；这是本地开发库只读冒烟，不代表生产长期监控数据。

风险和后续：

- 当前 `warning` 只是查询结果，不会发送邮件、Webhook 或 PagerDuty 通知。
- 指标接口尚无独立运维角色授权和请求频率限制。
- 实时聚合长期历史会随数据量增长变慢，需要结合 EXPLAIN 和真实数据量决定汇总策略。
- 尚无延迟直方图、模型调用次数、Token、降级率和业务工具可用率。

### 26. 持久化告警 Outbox 与并发去重

业务问题：指标接口只能在被查询时返回 `warning`。如果直接在查询接口中同步调用 Webhook，网络失败会拖慢请求，重试还可能重复通知；多个 Worker 同时评估同一窗口也可能产生告警风暴。

关键实现：

- `0010_agent_alert_outbox` 新增持久化 Outbox，保存告警指纹、评估窗口、错误数、阈值和 `pending`、`delivering`、`delivered`、`failed` 受控状态。
- `POST /api/v1/agent/alerts/evaluate` 复用指标聚合，只在达到阈值时入队；未触发时不写数据库。该端点要求已认证主体并校验当前 `quality_approver` 角色，避免公开请求制造 Outbox 数据。
- 指纹使用窗口小时数、生成时间的小时桶和当前阈值构造规范字符串后计算 SHA-256。普通重复请求先查询既有记录，并发竞争最终由数据库唯一约束裁决。
- 插入竞争触发唯一约束后，当前事务回滚并读取胜出记录；调用方通过 `queued` 区分本次新建与已存在，而两者都能取得相同告警 ID。
- `GET /api/v1/agent/metrics` 保持纯只读。显式 `POST` 才产生待投递事实，避免监控抓取或页面刷新产生隐式副作用。

边界取舍：本阶段没有连接 Webhook、邮件或 PagerDuty，也没有保存外部凭据。Outbox 的 `pending` 只表示告警已经可靠排队，不表示已经送达；后续 Worker 需要租约、超时回收、指数退避、最大重试次数、幂等投递键和送达确认。

遇到的问题：集成测试最初使用固定时间构造告警指纹，隔离测试容器在重复运行时保留了上一次记录，导致“首次创建”断言失败。修复方式不是清空数据库，而是让每个测试使用唯一时间窗口，并继续单独验证同一测试内的重复和并发去重。这保持了测试可重复性，也符合不依赖空数据库的原则。

真实验证：新增 6 项测试覆盖未认证拒绝、已认证但无角色拒绝、达到阈值入队、未触发短路、顺序重复去重、非法快照拒绝和两个独立数据库会话并发竞争。完整回归为 108 项通过，其中非集成 90 项、PostgreSQL 集成 18 项；开发库与测试库 `alembic check` 无漂移，`compileall` 和 `pip check` 通过。开发库从 `0009` 增量升级到 `0010` 后，原有 7 个文档、6 个分块及历史事件计数保持不变，新 Outbox 为 0 行。本阶段没有调用百炼、MES、QMS 或任何外部通知服务。

风险和后续：

- 当前复用审批角色作为最小运维权限，后续多用户身份体系应拆分独立 `alert_operator` 权限。
- 还没有负责领取与投递的 Worker，状态也尚未记录尝试次数、下次重试时间、租约持有者、送达时间和脱敏后的失败类别。
- 小时桶去重适合第一阶段抑制重复告警，但恢复通知、静默期和不同严重级别需要独立策略，不能只靠调整指纹。
- 阈值变化会产生新指纹，这是为了保留不同配置下的评估事实；频繁修改阈值时需要配置变更审计。

### 27. 租约式 Outbox Worker、重试与幂等 Webhook

业务问题：持久化 `pending` 记录只能保证告警没有丢失，不能保证真正送达。多 Worker 并发、进程在 HTTP 调用中崩溃、租约超时后旧 Worker 恢复，以及接收方返回 429/5xx 都会造成重复投递或状态覆盖。

关键实现：

- `0011_agent_alert_delivery` 为 Outbox 增加 `attempt_count`、`next_attempt_at`、`lease_token`、`lease_expires_at`、`delivered_at` 和 `last_error_kind`，数据库约束保证只有 `delivering` 状态能持有租约，只有 `delivered` 状态能持有送达时间。
- 领取 SQL 对到期 `pending` 和租约过期 `delivering` 记录使用 `FOR UPDATE SKIP LOCKED`；同一时刻一个 Worker 锁定记录，其他 Worker 跳过而不是互相阻塞。
- 领取提交后再执行外部 HTTP，避免持有长数据库事务。确认送达或失败时必须同时匹配记录 ID、`delivering` 状态和租约令牌；过期旧 Worker 即使稍后恢复也无法覆盖新租约结果。
- Webhook 使用稳定告警指纹作为 `Idempotency-Key`。载荷只包含告警 ID、窗口、错误计数、阈值和尝试次数，不发送错误原文、审批身份、问题、业务记录或内部租约。
- 超时、网络错误、HTTP 429 和 5xx 按有上限的指数退避重新进入 `pending`；普通 4xx 是不可重试拒绝，达到最大次数后也进入终止 `failed`。未知异常只记录固定 `unexpected`，不持久化异常字符串。
- `POST /api/v1/agent/alerts/process` 要求已认证运维角色；Webhook 未配置时先返回 503，不领取任务。同步入口默认处理一条、最多十条，便于外部调度器短批次调用。

为什么是至少一次：HTTP 成功响应可能在返回 Worker 前丢失，或租约在慢请求期间过期，因此发送端不可能仅靠本地状态证明“恰好一次”。稳定幂等键加接收端去重，配合租约令牌保护本地状态，形成可解释的至少一次投递语义。

配置与安全：远程 Webhook 强制 HTTPS，仅允许回环地址使用 HTTP 以支持本地测试；URL 和 Bearer Token 使用 `SecretStr`。租约时间必须长于单次 HTTP 超时，避免明显错误配置导致正常请求频繁被回收。

真实验证：新增投递阶段测试后，全量达到 123 项通过，其中非集成 103 项、PostgreSQL 集成 20 项。测试覆盖最小载荷与幂等头、HTTPS 约束、429/5xx/4xx 分类、未知异常脱敏、401、未配置 503、成功送达、并发只领取一次、租约过期回收、旧租约拒绝、延迟前不可领取和最终送达。开发库从 `0010` 增量升级到 `0011`，原有 7 个文档、6 个分块及全部历史事件计数保持不变，开发库和测试库均无迁移漂移。

运行验证：真实 Uvicorn 使用临时高熵测试 Key 和本机一次性 Webhook，处理接口返回 HTTP 200、`processed=1`、`delivered=1`；接收器确认稳定幂等键、正确告警 ID、事件类型和第 1 次尝试，数据库确认送达时间写入且租约释放。临时 Outbox 记录按固定 UUID 精确删除，接收器和 Uvicorn 均已停止；没有访问外网、百炼、MES 或 QMS。

风险和后续：

- 当前由认证 HTTP 端点触发短批次处理，尚无常驻 Worker、Cron/Kubernetes Job 示例和优雅停机排空策略。
- 通用 Webhook 只验证 HTTP 状态，不支持供应商签名、回执查询和恢复通知；接收端必须实现幂等键去重。
- 当前复用审批角色，后续 OIDC/RBAC 应拆分 `alert_operator` 权限并记录处理主体审计。
- 尚无投递延迟、积压量、重试次数和终止失败数的 Prometheus/OpenTelemetry 指标。

### 28. 应用内后台调度、故障隔离与运行状态

业务问题：即使具备可靠投递服务，如果仍需要人工或外部脚本调用处理端点，告警就不是自动闭环。同时后台任务不能因为一次数据库或网络异常退出，也不能在应用关闭后继续使用已经释放的连接。

关键实现：

- `AgentAlertScheduler` 启动后立即执行一个周期，随后按配置间隔串行运行；同一实例不会出现周期重叠。`start()` 幂等，重复调用不会生成第二个 Task。
- `SqlAgentAlertCycleRunner` 在独立异步 Session 中完成指标快照、阈值入队和最多 10 条 Outbox 投递，复用既有唯一指纹、租约和重试语义。
- 单周期捕获普通异常，只保存异常类名作为 `last_error_kind` 并增加失败计数；下一周期仍会继续。`CancelledError` 不被吞掉，应用关闭可以及时取消等待或正在进行的 HTTP 请求。
- FastAPI lifespan 在数据库和 LangGraph 可用后启动调度器；关闭顺序为调度 Task、Webhook Client、LangGraph、SQLAlchemy Engine，避免后台任务访问已关闭资源。
- 调度器默认关闭。`AGENT_ALERT_SCHEDULER_ENABLED=true` 时必须同时配置 Webhook；窗口、间隔和批量上限均由 Settings 做范围校验。
- `GET /api/v1/agent/alerts/scheduler` 只允许已认证运维角色查询，返回当前进程的运行状态、周期成功/失败数、累计入队和各类投递结果，不返回 Webhook URL、Token 或异常原文。

多 Worker 语义：每个 Uvicorn Worker 都可能运行自己的调度 Task，但小时窗口唯一约束会抑制重复入队，`SKIP LOCKED` 会抑制重复领取，因此正确性仍由 PostgreSQL 保证。多个 Worker 会重复执行指标聚合，所以规模扩大后应将同一 Runner 放入独立 Deployment、CronJob 或任务进程，而不是依赖进程内选主。

测试与验证：新增 8 项测试覆盖周期统计、异常类型脱敏、失败后下一周期恢复、启动幂等、取消停止、启用配置约束、401/403、禁用/启用状态和真实 SQL 周期投递。完整回归为 131 项通过，其中非集成 110 项、PostgreSQL 集成 21 项；`compileall`、`pip check`、`git diff --check` 和测试库 `alembic check` 均通过，本阶段没有数据库迁移。

运行验证：真实 Uvicorn 使用临时认证身份和显式调度配置启动，状态接口返回 `enabled=true`、`running=true`、`cycles_completed=1`、`cycles_failed=0`。开发库没有错误和待投递告警，因此累计入队与投递均为 0，没有调用本地或外部 Webhook。停止服务后开发库仍处于 `0011`，7 个文档、6 个分块及全部 Agent 事件和 Outbox 计数保持不变。

### 29. 检查点保留期、不可变归档与事务化恢复

业务问题：LangGraph 检查点保证流程可恢复，但长期保留会持续占用活动表，也让查询和升级风险增加。直接按线程删除无法证明数据已完整保存，解析 Checkpointer 私有 JSON 判断时间又会把生命周期绑定到第三方内部格式。

关键实现：

- `0012_checkpoint_archives` 为 `checkpoints` 增加数据库生成的 `created_at`。LangGraph 插入时无需感知新列；迁移前已有记录统一从迁移时间保守起算，不会立即成为过期候选。
- 归档使用四张规范化表：清单、checkpoint、blob、write。原始 JSONB 和二进制载荷在 PostgreSQL 内通过 `INSERT ... SELECT` 复制，不经过 Python 反序列化或 Base64 膨胀。
- 归档事务先对三张 LangGraph 表取得 `SHARE ROW EXCLUSIVE` 锁，再读取计数、复制、核对三类行数、按 write/blob/checkpoint 顺序删除活动副本。任一步异常都会 rollback，测试在复制后故意抛出删除故障，确认活动行和清单都没有半成品。
- 归档载荷触发器拒绝 UPDATE、DELETE、TRUNCATE；清单触发器只允许保持全部原字段不变的一次 `archived → restored` 转换，数据库所有普通 DML 都不能修改归档人、原始计数和归档时间。
- 恢复先检查目标线程在活动三表中完全不存在，再从不可变归档复制并校验计数；恢复只更新清单状态，不删除归档载荷，因此仍保留可审计快照。
- 活动归档使用按 `status='archived'` 的线程部分唯一索引，实现重复归档幂等；恢复完成后允许未来对同一线程生成新的归档历史。
- API 使用路径 UUID 与请求体 UUID 双重确认。预览是纯只读，返回候选线程和聚合数量；归档/恢复要求已认证运维角色，且恢复绝不覆盖活动状态。

为什么不自动归档：年龄只说明最后写入时间，不证明 Agent 业务已经完成。第一阶段提供候选预览和显式单线程确认，避免后台任务误归档仍需审批或排障的运行；后续若增加自动化，必须先有可靠终态字段或独立运行注册表。

不可变事件边界：审批和运行错误表已有防删除触发器，本阶段只统计截止时间前的数量，不绕过保护做清理。合规事件需要先确定法律保留期限、异地对象存储、校验和、加密和访问审计，不能与可恢复检查点使用同一删除策略。

测试与验证：新增 10 项测试后全量达到 141 项，其中非集成 114 项、PostgreSQL 集成 27 项。测试覆盖预览脱敏、401/403、确认 ID 冲突、近期检查点拒绝、真实归档/列表/恢复、重复操作幂等、活动状态防覆盖、复制后故障回滚以及归档载荷和清单防篡改。LangGraph 跨连接池恢复测试继续通过，开发库和测试库均无迁移漂移。

真实验证边界：开发库只从 `0011` 增量升级到 `0012` 并调用只读预览/列表；HTTP 200 返回无候选、三类历史计数为 0、归档列表为空。开发库前后均为 7 个文档、6 个分块，Agent 活动表、事件和归档计数均为 0。真实归档与恢复只在隔离 PostgreSQL 测试库验证，本轮没有删除开发数据。

风险和后续：

- 数据库内归档仍与主库共享故障域，不等于异地备份或 WORM 对象存储。
- 表级锁保证跨表快照一致性，但归档大线程时会短暂阻塞其他检查点写入；需要限制单线程规模并安排维护窗口。
- 归档快照长期增长后需要分区、外部导出和完整性校验；当前不提供归档载荷下载，避免轻易暴露完整 Agent 状态。
- 该阶段最初复用审批角色；后续 OIDC/RBAC 已拆分 `retention_operator` 与 `retention_reader`，归档和恢复由同一写权限承担。

## 30. 多用户 OIDC/JWT 与细粒度 RBAC

业务问题：单个服务端 API Key 能证明“请求来自受信服务”，但不能表达多个用户、独立角色或身份平台的密钥轮换；审批角色也不应自动拥有告警投递、指标读取和检查点归档权限。

技术方案：保留既有 API Key 兼容路径，新增可选 OIDC JWT 验证器。令牌形态决定认证路径，JWT 固定只接受 `RS256`，通过远端 JWKS 的 `kid` 选择公钥，并校验 issuer、audience、expiry 和 subject。PyJWKClient 的同步网络解析放入工作线程，JWKS 集合及签名密钥使用有界缓存。角色声明必须是字符串数组，只保留服务端认识的角色。

为什么选择该方案：固定非对称算法能避免把攻击者提供的 `alg` 当作信任输入，也避免对称密钥和公钥混用。显式 issuer/audience 防止其他系统签发的有效令牌被跨服务重放；服务端角色白名单防止身份平台新增声明时意外扩大权限。API Key 不立即移除，可让现有部署平滑迁移。

权限边界：`quality_approver` 只处理人工审批；`alert_operator` 可评估和投递告警，且隐含告警读取；`alert_viewer` 只读指标和调度状态；`retention_operator` 可预览、归档和恢复，且隐含保留期读取；`retention_reader` 只读预览和归档列表；`agent_admin` 具备全部 Agent 权限。API Key 的角色由配置项控制，默认保留历史能力。

安全约束：OIDC 开启时必须同时开启强制 Agent 认证并配置 issuer、audience 和 JWKS URL。生产 JWKS 只允许 HTTPS；development/test 仅为本地自动化允许 loopback HTTP。JWT 形态令牌在 OIDC 开启后不会失败回退为 API Key，避免认证降级。未知角色被忽略，非法角色声明直接返回 401。

测试与验证：新增 OIDC 单元测试后，全量达到 150 项，其中非集成 123 项、PostgreSQL 集成 27 项。覆盖有效 RS256、错误 issuer/audience、过期、非法 subject、错误角色声明、HS256 算法混淆、API Key 兼容、401/403 及各接口独立角色。另用内存生成的 RSA 密钥、本地 JWKS HTTP 服务和真实 Uvicorn 完成运行态冒烟：`retention_reader` 读取保留期预览为 200，读取指标为 403。

真实验证边界：自动化和冒烟只使用本地生成密钥与隔离测试库，没有连接企业身份平台、没有访问公网、没有改动开发库数据。JWKS 缓存可在未知 `kid` 时由库刷新，但尚未实现令牌撤销、内省、租户隔离或目录同步。

## 31. 后端初版收口：请求关联、Prometheus 与兼容分页

业务问题：业务链路可运行不等于服务可交付。没有请求关联 ID 时，HTTP 错误、应用日志和 Agent 运行 ID 难以串联；没有标准指标时只能人工查看进程；知识列表无分页能力则无法支撑数据增长。

技术方案：新增纯 ASGI 可观测性中间件和独立 Prometheus Registry。中间件校验上游 `X-Request-ID`，不合规时生成 UUID；完成响应时按 HTTP 方法、完整路由模板和状态码累计 Counter，按方法与路由模板记录 Histogram，并维护在途 Gauge。受权端点导出 Prometheus 文本。知识文档和分块列表增加可选 `limit/offset`，总数及窗口信息通过响应头返回，响应体继续保持原有数组结构。

为什么使用路由模板：实际路径可能包含文档 UUID、运行 ID 或其他业务标识，直接作为指标标签会造成高基数并泄露标识。中间件在响应开始阶段读取 FastAPI 有效路由上下文，记录 `/api/v1/knowledge/documents/{document_id}/chunks` 一类模板；404 统一记录为 `unmatched`。

兼容性选择：分页参数默认不传，旧客户端仍获得完整数组；新客户端显式传入窗口并读取 `X-Total-Count`、`X-Limit`、`X-Offset`。没有在初版中直接改成分页对象响应，避免破坏已有前端和集成调用。

安全边界：请求 ID 只接受长度受限的字母、数字及少量安全符号，拒绝空格和换行，防止日志注入。结构化访问日志不包含 Query、正文、实际路径参数、用户身份或模型内容。Prometheus 端点复用细粒度 RBAC，只允许告警读取/操作角色或管理员抓取。

测试与验证：全量达到 156 项，其中非集成 128 项、PostgreSQL 集成 28 项。测试验证安全请求 ID 透传与替换、模板标签不含实际业务值、监控端点 401/403/200、Prometheus 内容、分页总数/窗口、非法参数 422 和未分页兼容。真实 Uvicorn + 本地 JWKS 冒烟确认监控抓取返回 200，并包含真实 `/api/v1/ready` 指标。

遇到的问题：FastAPI 0.141 的延迟 Router 包装使 `scope["route"]` 在被 include 的路由中只表现为原始子路径。通过读取响应开始阶段的 FastAPI `effective_route_context` 获得完整模板，同时保留普通 Starlette Route 的回退逻辑。指标写入绑定到最后一个响应体消息，使紧随请求的抓取能确定看到上一请求。

风险和后续：当前独立 Registry 适用于初版单 Uvicorn 进程。Prometheus Python 客户端的多进程模式需要启动脚本管理 `PROMETHEUS_MULTIPROC_DIR` 并在 Worker 退出时清理；不能仅增加 Worker 数就假设指标自动聚合。后续再接入 OpenTelemetry Trace、模型 Token/降级指标和独立告警调度进程。

## 33. 真实 RAG 输入下的 JSON 尾部文字与有界纠正

问题：单条合成证据的模型冒烟成功，但真实关键词检索得到三条证据后，API 返回 deterministic_fallback。不能据此断言鉴权失败，因为兜底说明合并了配置与响应校验错误。

定位：读取用户运行的原始问题和三条证据，直接通过现有 Provider 重放。模型返回 HTTP 200，JSON 对象后追加了一段处置说明；Pydantic 报 json_invalid，具体为 trailing characters at line 2 column 1。因此网络、鉴权和模型可达性已通过，失败点在输出语法。

修复取舍：没有截取首个大括号片段、丢弃尾文或自动补证据。仅在自部署模式、首次 JSON 语法错误且响应不超过 16000 字符时，向同一模型追加原回答与明确的格式纠正指令，最多再调用一次。纠正保留原始证据；第二次结果继续走原有完整契约、引用范围和“动作必须有证据”校验。合法 JSON 的字段错误和引用错误不做格式纠正，百炼模式也不触发该步骤。

成本边界：格式纠正是一次生成中的额外请求，与外层网络重试分开。N 次网络重试下 HTTP 请求上界为 2 × (N + 1)，本地网络重试为 0。纠正会增加时延和推理消耗，不保证成功；再次失败仍安全降级。

真实边界：这证明该问题的格式故障已修复，并验证真实关键词检索到草稿的链路；不代表所有问题格式成功、引用语义忠实或根因分析质量已达标。旧检查点保存当时结果，代码修复不会自动重写历史运行；无 reload 的服务必须重启再提交新运行。

## 34. 前端工作台、离线规则路径与审批交互

业务问题：原项目主要通过 Swagger 调试，用户需要自行理解复杂 JSON。生成模型停机期间，如果前端只是继续发起模型请求，会遇到连接等待和降级，影响独立开发。

技术方案：在现有仓库的 frontend 目录增加 React + TypeScript + Vite 中文工作台，复用 FastAPI 所有业务接口。开发环境通过同源代理访问后端，避免把数据库或模型密钥放入浏览器。质量分析、知识库与检索分别组织页面，证据和草稿同时可见。

关键取舍：

- Agent 请求新增 use_model，默认 true 保留兼容，显式 false 时直接使用已有规则生成器。该选项只控制文本生成；配合 keyword 才能避免 Embedding 调用。仍执行检索、检查点持久化和人工审批。
- 前端检查 OpenAPI 是否包含新字段。旧后端会忽略未知输入字段，因此没有能力检查就可能让“规则草稿”实际上调用模型。
- 后端没有全库运行列表接口，前端只维护最多 20 个“本机最近打开”的运行 ID，并支持粘贴完整运行编号找回；不把本机记录数量包装成全库统计。
- 审批采用复核确认和独立确认窗口，相同运行/决定/复核人/备注的重试复用 UUID 请求编号。网络错误时保持不确定性提示，不把按钮点击当成成功；审批结果以服务端返回和后续查询为准。
- 审批凭据仅保存在内存，刷新清除，只在审批请求携带 Bearer。未认证兼容模式下的姓名明确显示为自填声明，不伪称已经认证。
- 文档和模型内容由 React 作为文本渲染，不插入原始 HTML。展示引用编号、分块原文和匹配分，并说明匹配分不等于结论正确率。
- 分析请求结束后检查用户是否仍停留在原页面，避免慢请求完成时把用户从知识库强制跳回；已创建运行仍加入最近打开记录。

测试结果：后端 159 项非数据库测试通过，新增用例确认显式 false 绕过生成器、true 与省略字段保留原路径；前端 9 项单元测试覆盖上传边界、API 错误、凭据发送范围、历史 ID 校验和审批请求编号。28 项数据库集成测试本轮未重跑。

## 36. SSH 监听不代表云端模型可用（2026-09-03）
