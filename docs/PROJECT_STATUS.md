## 当前架构

- PostgreSQL 17 与 pgvector 通过项目根目录的 `compose.yaml` 配置。
- 数据库数据保存在命名卷 `qualitypilot_pgdata` 中。
- 测试环境通过 Compose `test` profile 使用独立的 PostgreSQL/pgvector 容器、5433 端口、测试账号和 tmpfs，不挂载开发数据卷。
- FastAPI 后端位于 `backend/`，使用 Python 3.12、异步 SQLAlchemy、asyncpg 和 Pydantic Settings。
- 本地后端虚拟环境位于 `backend/.venv`。
- 后端运行时，开发环境 API 文档地址为 `http://localhost:8000/docs`。
- Alembic 已接管数据库结构变更；应用启动时只检查数据库连接。
- 上传原文件保存在配置项 `UPLOAD_DIRECTORY` 指定的目录，运行时上传目录不进入 Git。
- 已选定阿里云百炼 `qwen3.7-text-embedding`，固定输出 1024 维向量，后续使用余弦相似度检索。
- Embedding 的 API Key、专属接入地址、模型、维度、批量大小和超时时间已纳入 Pydantic Settings；真实密钥只保存在本地 `backend/.env`。
- 项目已初始化 Git，默认分支为 `main`，并连接到 GitHub 私有仓库 `csclly/qualitypilot`。
- WSL GitHub CLI 2.94.0 已持久安装在 `/home/qualitypilot/.local/bin/gh`，Git 凭据助手不再依赖 `/tmp` 临时路径。
- Agent 编排使用 LangGraph 1.2；检查点通过 `AsyncPostgresSaver` 持久化到 PostgreSQL，运行时依赖通过 context 注入，不进入可序列化状态。
- Agent 文本生成支持百炼和自部署两种模式；本地配置已切到微调 Qwen2.5（`pcb-qwen-lora`），源码默认值保留百炼兼容。自部署以提示词约束 JSON，百炼使用 JSON Mode；两种模式都通过本地 Pydantic 契约和证据编号范围校验。
- HTTP 可观测性使用独立 Prometheus Registry，统一输出请求量、路由模板延迟直方图和在途请求数；每个响应携带安全校验后的 `X-Request-ID`。

## 已知缺口

- 当前回填接口按单文档同步执行，尚无全库后台任务、持久化重试队列、失败任务状态和调用指标。
- 已完成合成小样本真实 Provider 基线，但没有真实企业 PCB 评测数据，当前指标不能代表生产效果。
- `pg_trgm` 是字符片段检索，不等同于中文语义分词或 BM25；尚未引入 Rerank，是否需要引入必须用更大真实评测集决定。
- 暂不支持扫描 PDF 的 OCR。
- Agent 已支持 API Key 与多用户 OIDC/JWT、JWKS 缓存和细粒度 RBAC，但尚无令牌撤销/内省、组织/租户隔离、目录同步、权限管理 API 或强制重新认证机制；OIDC 关闭时仍保留原有可选认证兼容模式。
- 节点错误已有聚合快照、阈值评估、持久化去重 Outbox、通用 Webhook 投递、可选应用内调度和单进程 Prometheus HTTP 指标，但尚无独立进程部署模式、多 Worker Prometheus 聚合、OpenTelemetry Trace、邮件/特定告警平台适配器、错误确认状态和运行级时间线。
- 检查点已有保留期预览、数据库内不可变归档和恢复能力；审批/错误事件目前只提供过期数量盘点并继续永久保留，尚未接入外部合规存储、法律保留策略和分区生命周期。
- 结构化生成已完成真实百炼端到端冒烟，但尚无系统化引用忠实度、提示注入和生成质量评测；本阶段的业务上下文验证来自内存假工具，不代表已连接实时 MES/QMS。
- MES/QMS 只读工具已接入 Agent 状态机，但尚无真实系统认证、字段映射、网络适配器、工具级重试、熔断和可观测性。
- 尚无工单写入能力；未来写操作必须使用独立权限、审批、幂等和审计链路，不能扩展当前只读协议绕过边界。

## 当前实施决策

- 文件导入采用 20 MB 上限的同步处理；大文件或高并发需求出现时再引入持久化任务队列。
- 原始文件使用生成名称保存，数据库记录原文件名、MIME、大小、SHA-256、存储名和处理时间。
- TXT/Markdown 支持 UTF-8 与 GB18030；PDF 和 DOCX 使用独立解析适配逻辑。
- 文档元数据和分块在同一数据库事务中写入，不允许部分分块残留。
- 中文文本优先在段落和句子边界切分，并记录字符起止位置。
- Embedding 采用阿里云百炼 `qwen3.7-text-embedding`，显式指定 1024 维，向量检索使用余弦相似度。
- 数据库向量字段使用受保护的 Alembic 增量迁移调整为 1024 维；迁移和回退在存在非空向量时都会拒绝执行，避免静默转换或损坏已有向量。
- 新文档上传默认生成向量；云端调用发生在文件落盘和数据库事务之前，调用失败不会留下文件或数据库半成品。
- 历史回填先结束只读事务再调用云端，写回时使用 `embedding IS NULL` 条件更新，避免长事务和并发覆盖。
- API Key 使用 Pydantic `SecretStr` 承载，配置允许为空，使健康检查、旧接口和不调用模型的测试不依赖真实云端密钥。
- 自动化测试统一覆盖数据库连接、运行环境、上传目录和 API Key；测试库名不以 `_test` 结尾时立即拒绝运行。
- 本地测试数据库使用 Compose profile 按需启动并存放于 tmpfs；CI 使用 GitHub Actions job 级 PostgreSQL 服务，两者都不复用开发数据卷。
- Provider 通过协议与工厂创建，普通自动化测试注入 `httpx.MockTransport` 或假 Provider，不会读取真实密钥、访问公网或消耗模型额度。
- 查询先检查是否存在非空向量；空库直接返回空列表。非空时生成查询向量，用 pgvector `<=>` 计算余弦距离，并返回 `1 - distance` 作为相似度。
- HNSW 索引只覆盖非空向量，使用与查询运算符匹配的 `vector_cosine_ops` 操作符类。
- 评测按稳定文档编号标注相关性，Recall@K 对相关文档去重后计算，MRR 使用首个相关分块排名。
- 搜索请求默认 `vector` 以保持现有接口行为；`keyword` 不调用云端，`hybrid` 才同时使用两路候选。
- 中文关键词第一版选择 PostgreSQL 内置 `pg_trgm`，避免引入镜像中不存在的中文分词扩展；它适合术语和字符片段匹配，但不是完整中文分词。
- 关键词距离使用 `<->>` KNN 运算符与 `gist_trgm_ops` 对齐；SQLAlchemy 使用 `type_coerce` 而不是 SQL `CAST`，避免破坏索引排序。
- 两路分数不可直接线性相加，因此使用 RRF 按排名融合；默认候选倍率为 5、`rrf_k=60`，均通过 Pydantic Settings 校验。
- 引用正确率要求检索分块同时来自相关文档且包含至少一个人工标注证据短语；当前按查询计算后取宏平均。
- 真实基线同时保存 Top-1 和 Top-3：前者衡量首条引用质量，后者衡量扩大候选集后的召回能力。
- 评测运行器只对网络错误、HTTP 429 和 5xx 做最多 2 次指数退避重试；普通 4xx 不重试，重试耗尽仍明确失败。
- Agent 可恢复状态只保存字符串、数值、证据和草稿；数据库会话、Provider 工厂和生成器放在 LangGraph runtime context。
- 审批节点使用 `interrupt` 暂停，通过相同 `thread_id/run_id` 和 `Command(resume=...)` 恢复；重复审批返回 409。
- LangGraph 官方检查点结构由 `0006` Alembic 迁移创建，应用运行时不调用 `setup()`；数据库结构始终由项目迁移历史统一管理。
- 检查点包固定为 `langgraph-checkpoint-postgres==3.1.1`，升级依赖时必须同步审查其迁移定义与项目 Alembic。
- 检查点使用独立 psycopg 异步连接池，启用 `autocommit`、`dict_row` 和 `prepare_threshold=0`，连接池大小由 Pydantic Settings 校验。
- `0006` 降级前检查状态表；存在任何 Agent 运行状态时主动拒绝，以防误删可恢复任务。
- 未选定文本生成模型前不伪造 AI 根因分析，批准前不产生最终响应。
- 文本生成使用 `qwen3.7-max-2026-05-20` 非思考模式和 JSON Mode；固定快照便于复现并优先消耗较早到期的免费额度。JSON 只保证语法，本地 Pydantic 继续校验字段、长度和禁止额外字段。
- 提示词中的证据使用 1 开始的临时编号，模型只返回编号；服务端验证范围后映射到检索结果中的分块 UUID，模型无权自行生成来源标识。
- 模型输出不合约时不把半可信内容交给审批，而是降级到确定性草稿；`generation_mode` 明确区分 `model` 与 `deterministic_fallback`。
- MES/QMS 第一阶段只定义读取协议，接口层不存在任何写方法；生产写入能力不能通过给只读实现增加开关来启用，未来必须使用独立协议、独立权限和幂等审批链路。
- 多个业务系统查询使用并发聚合，每个工具单独设置超时和失败结果；单个系统故障不取消其他系统的有效结果。
- 工具返回记录必须与声明的 MES/QMS 来源一致、ID 唯一且不超过请求上限；适配器的未知异常只返回脱敏分类，不暴露内部连接信息。
- 业务工具实例继续放在 LangGraph runtime context，检查点只保存纯字典和标量；适配器对象、连接和凭据不会被序列化。
- 业务记录属性限制为最多 20 个标量字段，并限制名称、摘要和文本值长度；真实适配器仍需在边界处做字段白名单映射，不能直接持久化供应商原始响应。
- 模型只返回从 1 开始的临时业务编号；服务端验证后映射为 `tool_name + record_id`，与知识分块 UUID 引用采用相同的“模型不生成真实标识”原则。
- 审批审计事件先提交数据库，再恢复 LangGraph；如果工作流投影暂时失败，同一 `request_id` 可以安全重放，而不会生成第二个决策。
- 未认证兼容路径中的 `actor_id` 只是经长度和空白校验的客户端声明；认证成功后服务端配置身份会覆盖请求体，审计中的 `actor_authenticated` 和 `auth_method` 用于区分两者。
- 审批 API Key 只以 SHA-256 摘要保存在服务端配置中，原始随机 Key 只交给客户端；它作为单服务账号兼容路径保留，多用户场景使用已实现的带签名和过期时间 OIDC/JWT。
- 工作流节点只附加阶段并保留原异常为 `cause`；API 边界统一分类和脱敏，避免业务节点自行决定 HTTP 状态或泄露供应商错误文本。
- 错误历史只记录导致工作流中断的异常。业务工具的可预期部分失败继续保存在业务故障 DTO，文本模型失败降级继续通过 `generation_mode` 和风险说明表达。
- 错误历史写入失败不会覆盖原始业务错误响应；当数据库自身不可用时可能无法留下错误事件，因此后续仍需要独立日志、指标或外部遥测作为第二通道。
- 指标查询直接聚合不可变审批和错误事件，不维护可能漂移的计数器表；第一版窗口限制为 720 小时，后续数据量增长时再评估汇总表或时序数据库。
- `warning` 只是当前快照状态，不代表外部通知已经送达；阈值由 Settings 校验，主动告警必须另建带去重、静默和恢复通知的投递机制。
- `POST /api/v1/agent/alerts/evaluate` 是显式有副作用的运维操作，只允许已认证且具有 `alert_operator` 或 `agent_admin` 的主体调用；只读指标 `GET` 不会隐式写入 Outbox。
- 告警指纹由窗口小时数、UTC 小时桶和阈值生成 SHA-256；数据库唯一约束是最终并发防线，相同窗口重复评估返回既有 `pending` 记录。
- Webhook 投递采用至少一次语义：租约可能在慢请求期间过期，因此接收方必须依据稳定 `Idempotency-Key` 幂等处理；数据库租约令牌阻止旧 Worker 覆盖新 Worker 的结果。
- 告警租约必须长于单次 HTTP 超时；重试使用有上限的指数退避，非重试型 4xx 或达到最大尝试次数时进入终止 `failed`。
- 同步运维处理端点默认只处理 1 条、最多 10 条，避免单次请求被多个 Webhook 超时长时间占用；生产调度应以短批次重复触发，后续可拆为独立常驻进程。
- Webhook URL 和可选 Bearer Token 使用 `SecretStr`，远程地址强制 HTTPS；载荷不包含审批人、问题文本、错误消息、业务记录或租约令牌。
- 应用内调度器默认关闭；显式启用时 Webhook URL 是必填项。每个周期立即评估 1—720 小时窗口并最多处理 10 条，单实例内周期不重叠。
- 多 Uvicorn Worker 会各自启动调度器，但小时窗口指纹唯一约束和 `SKIP LOCKED` 保证数据库层去重与并发领取安全；代价是重复指标查询，因此高规模部署应改用独立调度进程。
- 调度器状态是当前进程内存快照，不是跨 Worker 全局指标；持久告警事实仍以 PostgreSQL Outbox 为准，后续应导出外部可观测指标。
- 检查点保留期只依据数据库 `created_at`，不解析 LangGraph 私有 JSON；迁移前已有记录按 `0012` 应用时间保守起算，避免误把无法确认年龄的状态立即归档。
- 归档操作按线程 UUID 执行，并要求请求体重复确认；年龄达到阈值只是候选条件，不自动代表业务已完成，运维仍需结合运行状态确认。
- 为避免检查点、Blob 和 Write 在复制期间产生跨表不一致，归档/恢复短时取得三张表的 `SHARE ROW EXCLUSIVE` 锁；当前低频治理场景可接受，高规模部署应迁移到分区或专用维护窗口。
- 归档数据继续保存在 PostgreSQL 中且永久防篡改，恢复不会删除归档快照；这保证可恢复和审计，但不是异地备份，仍需数据库备份和外部合规存储。
- 审批和错误事件的数据库触发器继续禁止删除。本阶段只盘点过期数量，不绕过触发器清理；未来外部归档必须先定义法律保留、校验和与授权流程。
- 审计表采用追加一次、禁止常规 DML 修改的边界；降级前必须先完成显式合规归档，不允许迁移脚本自动删除历史。

## 安全约束

- 不得删除或重建数据库及其 Docker 数据卷。
- 不得运行 `docker compose down -v`。
- 数据库结构变更必须使用并审查 Alembic 增量迁移。
- 不得暴露 `.env` 的值或提交密钥。
